摘要

swift-section interface --resolve-c-module-names 能把公开的 C 导入类型写到真实模块下（__C.CGColorRef → CoreGraphics.CGColor），私有的 CF 类型却查不到模块：SDK 里没有它们的头文件，依赖镜像的 Objective-C 元数据也不列 CF 类型，于是按 0106 的规则只印描述符给的裸名（CGSVGDocument）。

本提案在 SwiftTypeNameResolution 里新增 CFDeclaredTypeNames，它是 swift-type-indexing 的 DeclaredTypeNameSource 的又一个实现：从镜像的导出表里找出每个 …GetTypeID 函数，列出它定义的 CF 类型（_CGSVGDocumentGetTypeID → CGSVGDocumentRef）。SwiftInterfaceBuilderTypeNameProvider 为根镜像和每个直接依赖各登记一个。之后 CGSVGDocumentRef 归到 CoreSVG，引用印成 CoreSVG.CGSVGDocument。打印器、swift-type-indexing 和 CLI 参数都不改。

要你定

两件事

  1. 实现形式：用 swift-type-indexing 现成的 DeclaredTypeNameSource 注册表（提案的做法），而不是在打印器上另注册一个解析器（讨论时最先选的方向）。理由见替代方案第 1 条。
  2. 调研第 10 条的 IOSurfaceRef 疑似问题（可能被印成 IOSurface.IOSurface）：是否先在 Ultra 上复现，再另行修复。

提议方案

  1. 新增 CFDeclaredTypeNames，与 ObjCDeclaredTypeNames 同形：init(machO:imagePath:)，declaredTypeNames() 读 machO.exportedSymbols，每个名为 _<名字>GetTypeID 的导出给出 <名字>Ref；<名字> 以下划线开头的私有函数（__LSASNGetTypeID）同时给出去掉前导下划线的拼写（LSASNRef）。
  2. provider 登记它：来源变成「根镜像的 CFDeclaredTypeNames，然后每个直接依赖依次是 ObjCDeclaredTypeNames、CFDeclaredTypeNames」。根镜像排第一，它自己定义的类型由它自己说了算；根镜像不进 moduleFilter，不触发 SourceKit 接口生成。
  3. 打印器、swift-type-indexing、CLI 参数都不改，只补帮助文字和 skill 说明。

非目标

  • 跟着重新导出找子框架（LSASNRef → CoreServices）：ObjC 来源同样不跟，两边一起做，另开提案。
  • 间接依赖（CFPhoneNumberRef）：放宽到传递闭包会让 SourceKit 接口生成回到几百个模块，另开提案。
  • 没有 GetTypeID 导出的类型，以及非 CF 的私有 C 类型：二进制里没有可靠的模块证据。
  • 没有描述符时给出 Swift 名：仍印 模块.XRef。
  • 根镜像自己的 Objective-C 类、dump、RuntimeViewer 接入（发版后在它那边加一行）、IOSurfaceRef 疑似问题。

详细设计

API 
public struct CFDeclaredTypeNames<MachO: MachORepresentable & Sendable>: DeclaredTypeNameSource {
    public let imagePath: String

    private let machO: MachO

    public init(machO: MachO, imagePath: String)

    /// The typedef name of every CF type the image exports a `GetTypeID` function for.
    public func declaredTypeNames() async -> [String]

    /// `_CGSVGDocumentGetTypeID` → ["CGSVGDocumentRef"], `__LSASNGetTypeID` → ["_LSASNRef", "LSASNRef"].
    static func typedefNames(forExportedSymbolName symbolName: String) -> [String]
}

extension SwiftInterfaceBuilderTypeNameProvider {
    static func declaredTypeNameSources(root: MachO, dependencies: [MachO]) -> [any DeclaredTypeNameSource]
}

形状照 ObjCDeclaredTypeNames 抄。泛型约束只要 MachORepresentable & Sendable：exportedSymbols 是 MachOKit MachORepresentable 的要求，MachOFile、MachOImage 和包装类型都有，不需要判断读取器种类。协议要求是 async throws，实现不会失败，写成不抛错的 async。

命名规则
  1. 导出名必须以一个 _ 开头，去掉它得到 C 函数名；Swift 符号和 Objective-C 符号因为不以 GetTypeID 结尾自然落选。
  2. C 函数名以 GetTypeID 结尾，去掉后缀的部分非空、由字母数字和下划线组成、不以数字开头，记为 base。
  3. 给出 base + "Ref"；base 以下划线开头时，再给出去掉全部前导下划线后的 + "Ref"。
  4. CFGetTypeID 给出的 CFRef 这类不是类型的名字不做过滤：只在查询恰好问到它时才命中，而那时 SDK 的归属已经先问过了。
性能

TypeDatabase 只在一个名字查不到时才按顺序读下一个来源。根镜像排第一，第一次未命中就会读一遍根镜像的导出表：SwiftUICore 这样的大镜像有数十万个导出。第 3 步在 Ultra 上量一次耗时变化；明显的话，改成直接遍历导出 trie、只取以 GetTypeID 结尾的名字。

调研

十条查证过的事实
  1. 哪些是 CF 类、怎么枚举：ClangImporter 把指向带 objc_bridge 系列 attribute 的 struct 的指针 typedef 导入成 ForeignKind::CFType 的类，并合成 _CFObject 一致性；描述符种类是 class，import info 写着 N<typedef 名> 和 St。ipsw dyld swift --foreign 导出 dyld 预存的 __C 一致性表，按 _CFObject 筛出 66 个 CF 类。
  2. 模块不在二进制里：描述符挂在 __C，合成的一致性在 __C_Synthesized。Swift 取顶层 Clang 模块（ClangImporter.cpp:3143-3154），LaunchServices 的类型属于 CoreServices。
  3. GetTypeID 的镜像就是模块：46 个公开 CF 类全部一致；私有的 20 个里 17 个能找到导出；Core* 框架约有 190 个不在公开 SDK 里的 …GetTypeID。
  4. 打印器已经会用描述符的名字：引用处模块解析后，标识符依次取解析器的 Swift 名、0106 名字表、C 名（TypeNodePrintable.swift:186-268），声明行同理（SwiftDeclarationPrinter+Headers.swift:153-183）。
  5. swift-type-indexing 已有开放注册表：DeclaredTypeNameSource，SDK 答不上时按登记顺序读，第一个声明者胜出；这个包自己不读 Mach-O；ObjCDeclaredTypeNames 是现有唯一实现，不含 CF 类型。
  6. 去 Ref 规则只认 SDK 里有的名字：私有 CF 类型拿不到解析器给的 Swift 名，走描述符那一档，AGGraphRef 正确地印成 Graph。
  7. 现在谁被登记：provider 只给直接依赖登记 ObjC 来源，根镜像不登记；只有 interface --resolve-c-module-names 接上它；RuntimeViewer 自己给打开的每个镜像登记来源。
  8. 覆盖面：直接依赖覆盖 14 个，登记根镜像后 15 个；剩下的是重新导出（1）、间接依赖（1）、没有导出（3）。
  9. 带 Ref 的名字在 Swift 里不能用：只剩改名用的兼容别名；没有描述符时会印成 CoreSVG.CGSVGDocumentRef。IOSurfaceRef 因为和 ObjC 类 IOSurface 重名而保留 Ref。
  10. 顺带发现、未验证：去 Ref 规则不看重名，而打印器先问解析器，__C.IOSurfaceRef 可能被印成 IOSurface.IOSurface。

替代方案

六条被否或推迟的方向
  1. 打印器上另注册一个 ModuleNameResolving：否。注册表已经在 swift-type-indexing，另写一个要么抄一遍规则，要么与 TypeDatabase 给出不同答案；RuntimeViewer 也走 DeclaredTypeNameSource。
  2. 让 swift-type-indexing 自己读导出表：否，那个包按设计不读 Mach-O。
  3. 从 CF 运行时类注册取名字：否，要反汇编调用点，结果与导出表等价，名字还是显示名。
  4. 用一致性符号里的模块：否，那是声明一致性的模块，不是类型的模块。
  5. 让去 Ref 规则也认运行时名表：否，会把 IOSurfaceRef 改成 IOSurface，还会把 Graph 改坏成 AGGraph。
  6. 跟着重新导出算进伞框架：推迟，与 ObjC 来源一起另开提案。

影响

  • 源码兼容性：纯新增，provider 的公开接口不变；--resolve-c-module-names 下私有 CF 类型会带上模块。
  • ABI：不适用，SPM 源码分发。
  • 下游：InterfaceRequest 自动受益；没有基线开着 __C 模块解析，渲染 A/B 不受影响；RuntimeViewer 要在 RuntimeSwiftSection.swift:2013 加一行才受益；MachOKitUI、SymbolViewer 不受影响。
  • API 演进：没有被替代的旧 API，按 minor 版本发布。
