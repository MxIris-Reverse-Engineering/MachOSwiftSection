摘要

把 MachOSwiftSection 的 TypeIndexing target（SDK 模块索引、API notes 索引、ObjC 元数据归属、按 SDK 版本的磁盘缓存）整体搬进新的独立包 swift-type-indexing，模块名仍是 TypeIndexing。新包不依赖 MachOSwiftSection，也不依赖 MachOObjCSection：原来直接调用 ObjCIndexing 补私有类归属的那一层，改成新包声明的协议 DeclaredTypeNameSource，由 MachOObjCSection 实现。

搬家同时修两处错误：

  • API notes 的改名规则：只有 SwiftPrivate 的类型要加 __ 前缀，有 SwiftName 的直接用它——现在两种都不改名。
  • sourcekitd 只认 Xcode 的目录结构，只装 Command Line Tools 时找不到。

之后三方接入：

  • MachOObjCSection：打印 ObjC 头文件时，按 API notes 在类、协议、category 及其成员上标出 NS_SWIFT_NAME(...) / NS_REFINED_FOR_SWIFT。
  • MachOSwiftSection：删掉 TypeIndexing target，只留一个薄适配层；swift-section interface --resolve-c-module-names 照常可用，swift-section objc 加一个同类开关。
  • RuntimeViewer：在找得到对应平台 SDK 的 Mac 上，默认把 __C.UICellConfigurationState 打印成 UIKit.__UICellConfigurationState。索引在 engine 连上后后台预建、进 Report；建好前先显示 __C.，建好后自动刷新；MCP、命令行与导出一起换成解析后的名字。

要你定

没有待你决定的事

提案已批准；swift-apinotes 0.3.0 与 swift-type-indexing 0.1.0 已经批准推送并打了 tag。

agent 自己定的（可以推翻）

  • MCP、命令行、导出与 Find 语料构建等索引就绪（或确认不可用）再打印；只有界面先显示 __C.。
  • 两个开关放在 Generation Options 面板（Swift 组、ObjC 组），不放 Settings：现有打印开关都在这里，随请求发出、进缓存键、命令行也读同一份。
  • 缓存放 ~/Library/Caches/<App 的 bundle id>/TypeIndex/，不是 RuntimeDerivedDataKind；Delete Derived Data 一起删。
  • 新仓库不迁移 git 历史；MachOSwiftSection 不保留旧 product 的转发层。

模块依赖：改了什么

箭头从使用方指向依赖。RuntimeViewerCore 还直接依赖 ObjCTypeIndexing 与 TypeIndexing（建 TypeDatabase、取 ObjC 标注），图里省略；三个新依赖都只在 macOS 上。红色虚线是删掉的旧依赖：MachOSwiftSection 的 TypeIndexing 直接调用 ObjCIndexing。swift-apinotes fork 把 ObjCContext.methods / properties 改成 public 并打 0.3.0，ObjC 成员的标注才有来源。

新包内部

TypeDatabase                                   (actor, no longer generic)
├── SDKIndexer.discover()           -> .swiftmodule list, .apinotes files       (no sourcekitd)
├── ModuleInterfaceIndexer          -> type names per module                    (sourcekitd; skipped when missing)
│   ├── SourceKitManager
│   │ + └── SourceKitLocator        -> Xcode toolchain | Command Line Tools
│   └── ModuleIndexCache            ~ directory injected by the caller
├── APINotesIndex                   ~ SwiftName wins; SwiftPrivate alone -> "__" + C name
│                                   + ObjC container entries (methods, properties)
- ├── ObjCInterfaceIndexer (MOS)
+ └── [any DeclaredTypeNameSource]   -> lazy fallback, first image wins

RuntimeViewer 的建立与刷新

打印的服务进程（本机、Catalyst、文件、框架四个 service，Catalyst helper，独立的命令行 host）启动时打开索引。Swift section 第一次为一个镜像配置时（开关开着）请求一批：平台取镜像的 LC_BUILD_VERSION，内容是它链接的模块和它自己的 ObjC 元数据；SDK 不可用就记下原因、不排批次。同一平台的批次依次执行，每批完成把平台的 generation 加一：section 下次配置时重新注册解析器、清掉自己的接口缓存，engine 广播 .typeNamesResolved，App 的 ContentTextViewModel 先清 RuntimeInterfaceCache 再重新取。最下面是两类请求：界面立刻打印（这个镜像那一批完成前是 __C.），MCP、命令行、导出与 Find 语料等这个镜像那一批完成再打印。

RuntimeViewer
  • 进程开关：RuntimeTypeNames.enableInThisProcess() 照 RuntimeDerivedData.enableInThisProcess() 的样子：四个 XPC service、Catalyst helper 与独立的命令行 host（CommandLineHostServer.start()，kind == .standalone 时；App 当 host 时打印在 App 的 service 里）在入口处打开。其余进程——App 本身、注入的 payload、iOS 设备、测试——都不打开，照旧印 __C.，也从不读 SDK、不写缓存。忘了调用不会坏事，只是那个进程不解析。
  • 进程内的索引：RuntimeTypeIndex 是每个打印进程一个的 actor（static let process）。它不经 @Dependency：RuntimeViewerCore 不依赖 swift-dependencies，能碰到它的只有 engine 与 section，和 RuntimeDerivedData 一样。按 SDKPlatform 各持一个 TypeDatabase：
    • 平台：一律取镜像第一个 LC_BUILD_VERSION 的平台（RuntimeTypeNames.platformName(of:)，macCatalyst 映射到 .macCatalyst），共享缓存镜像、磁盘文件与已加载镜像同一条规则。没有这个 load command 的旧镜像不解析。
    • 批次：RuntimeSwiftSection.updateConfiguration 第一次为一个镜像配置时（resolvesImportedTypeNames 开着）调 request(_:)，交出这个镜像链接的模块名（machO.dependencies 的 install name 推出模块名）和它自己的 ObjCDeclaredTypeNames。新模块、新镜像才排一批；平台的第一批同时读 API notes。同一平台的批次串起来依次执行，所以不会重复建。依赖镜像里的私有类型，要等那个依赖自己被打开（后台索引迟早会开）才算进来——不为打印一个镜像去打开它全部依赖的 ObjC 元数据。
    • 不可用：TypeIndexingAvailability 不可用时记下原因，不排批次，打印器不注册解析器，输出保持 __C.。
    • 内存：每个打印的服务进程各有一份（本机、Catalyst、每个文件、每个框架实例），落地时量一次 malloc 在用量写进提案（步骤 9）。
  • 打印：每批完成把平台的 generation 加一。RuntimeSwiftSection 记着自己注册解析器时的 generation，下次配置时发现变了，就按当前选项重建完整的解析器列表（opaque 解析器 + 类型名解析器，互不误删），清掉 interfaceByObject / importedInterfaceByObject；语料打印器同样按 generation 重建。批次完成时 engine 把监听回调转成 broadcast(.typeNamesResolved(platformName:))（startObservingTypeIndex()，每个 engine 一次）。ObjC 头文件在 marksSwiftNamesFromAPINotes 开着时，把 swiftImportNotes(forClassNamed:/forProtocolNamed:platform:) 的结果与 objcSwiftImportNotes(for:) 合并；category 按它的类查。
  • 等待：GenerationOptions.waitsForTypeIndex 为 true 时，updateConfiguration 等这个镜像那一批完成再打印；false（界面）时直接打印。MCP（.mcp 预设）、命令行（每种选项来源都置 true）、导出（exportGenerationOptions）等待；Find 语料打印前一律等待（waitForTypeIndex(of:)）。等待只在磁盘缓存冷、第一次生成某个 SDK 版本的模块接口时明显。
  • 兼容性：三个新选项都用 @Default，旧版对端解码时取默认；RuntimeDataChange 新 case 只由新版 Mac 服务发出，旧对端不会收到也不会发出；typeIndexStatus 命令对旧对端没有处理器，XPC 上没有处理器的命令被丢弃而不是回错，所以 typeIndexStatus() 经 dispatchToServingProcess(_:timeout:) 用连接自带的 2 秒超时发出，超时或出错都答 .empty，Report 里不显示这一类。
  • 语料 variant：RuntimeInterfaceCorpusSnapshot 的 variant 加一段 RuntimeTypeNamesCorpusVariant.component：开着索引、找得到 macOS SDK 时是 TypeNames-<SDK 版本-build>（共享缓存的 macOS 与 Mac Catalyst 镜像都对着 macOS SDK 读），否则 UnresolvedTypeNames。
  • 缓存位置：RuntimeTypeIndexLocation 从进程的 Bundle.main 往上找第一个是 RuntimeViewer 的 .app（RuntimeDerivedDataLocation.enclosingApplication），用 ~/Library/Caches/<bundle id>/TypeIndex，与 DerivedData 并列；App、它的 XPC service 与内嵌的命令行工具因此共用一份。不在 App 里的命令行工具用 ~/Library/Caches/runtime-viewer-cli/TypeIndex。Delete Derived Data 一并量它、删它（先改名再后台删）。
  • 界面：Generation Options 面板的 Swift 组「Resolve Imported Type Names」、ObjC 组「Mark Swift Names From SDK」，都默认勾选。Report 新类别「Imported Type Names」（排在 Cross References 之后），每个平台一行：建立中（第几批 / 共几批）、就绪（模块数）、不可用（没有开发者目录 / 没装这个平台的 SDK），类别行带缓存大小；没有平台时整类不显示，没有取消、推出、清除。TypeIndexCoordinator 照 CrossReferencePreparationCoordinator：启动时、每次 .typeNamesResolved、engine 换进程时问一次状态，建立中每 2 秒问一次；建立中算进 isWorkInProgress（防 App Nap），工具栏显示 Indexing Imported Type Names。内容区收到 .typeNamesResolved 先在主线程清文档的接口缓存再重新取，避免缓存自己的清空排在重新取之后。

调研

二进制里为什么没有 Swift 名与模块
  • Swift 给导入的 ObjC 类做 mangling 时用 ObjC 运行时名（ASTMangler.cpp 的 tryAppendClangName）。UIKit.tbd 里 $s5UIKit24UICellConfigurationStateV19_bridgeToObjectiveCSoABCyF 的 SoABC 直接复用了结构体名那个标识符；PKDrawing、UTType 的符号形状完全相同。
  • 改名只在 SDK 里：UIKit.apinotes 的 SwiftPrivate: true、PencilKit.apinotes 的 SwiftName: PKDrawingReference。
SDK 统计：为什么不能在二进制层面推断
同名又桥接的类型数量例子
__X（SwiftPrivate）6UIKit 的 UICellConfigurationState、UIViewConfigurationState、UIPointerShape……
XReference（SwiftName + SwiftBridge）14PencilKit 8 个、NSDiffableDataSource(Section)Snapshot、UTType、INShortcut
私有框架，SDK 无资料2ASCredentialProvider、WFVariableString

另有 15 个 __ 类型与对应 Swift 类型不同名（如 NSMorphology ↔ Morphology）。

编译器的改名规则与现有实现的偏差
  • ImportName.cpp：有 swift_name 时直接用它并提前返回，不加 __；没有时才对 swift_private 加 __。
  • 现有 APINotesIndex.swift:117 两种都不改名；测试 swiftPrivateEntitiesAreAttributedButNotRenamed 断言了后一种。来历是提案 0009 落地时（2026-08-22）沿用历史实现的保守做法，文档里没有给理由。
sourcekitd 与 Command Line Tools
  • 现有代码拼 <developer dir>/Toolchains/XcodeDefault.xctoolchain/…；Command Line Tools 下 sourcekitd 在 /Library/Developer/CommandLineTools/usr/lib/sourcekitd.framework（本机核对）。
  • Command Line Tools 自带 MacOSX.sdk，含 iOSSupport 的 UIKit.apinotes；iOS 等其他平台的 SDK 只有 Xcode 里有。
  • API notes 不需要 sourcekitd，只有「模块接口里的类型名」这一层需要。
三个仓库的现状要点
  • MachOSwiftSection：12 个文件里 9 个可原样搬走；APINotesIndex、TypeDatabase 要解耦；适配器留下。CImportedTypeNameCategory 打印器自己也用，不能搬。缓存目录写死、调用方无法指定。组织里没有外部使用方。
  • MachOObjCSection：Note 只有 isRefinedForSwift；只有类的入口接收标注；包支持 macOS 10.15 而 TypeDatabase 要求 macOS 13。
  • RuntimeViewer：每个镜像自己的打印器，从未注册类型名解析器；关 opaque 开关会清掉所有解析器；打印都在服务进程；内容区只在对象或选项变化时重取；独立命令行 host 没有 derived data 位置。
  • swift-apinotes 依赖 MetaCodable（宏包，构建时要 swift-syntax）与 Yams；它和 SourceKitD 已经经 MachOSwiftSection 进了 RuntimeViewer 的依赖图。

替代方案

9 条被否的路径
  • 二进制层面推断：同名桥接 20 个里 14 个是 XReference，与 __X 无法区分。
  • 新包留在 MachOSwiftSection：MachOObjCSection 需要同一份数据，却不能反向依赖。
  • 新包继续依赖 ObjCIndexing：ObjC 一侧接入后会成环，改为协议注入。
  • ObjC 一侧另起提案：用户选择一并做。
  • RuntimeViewer 默认关：用户选择找得到 SDK 就自动开。
  • 界面等建好再显示：用户选择先显示 __C.、后台预建、建好刷新。
  • MCP / 命令行 / 导出保持 __C.：用户选择一起换。
  • 开关放 Settings 新分支：要另造一条把设置送进服务进程的通道。
  • 缓存作为 RuntimeDerivedDataKind：derived data 按 dyld 共享缓存分目录，类型索引按 SDK 版本，两者无关。
