摘要

把 MachOSwiftSection 的 TypeIndexing target（SDK 模块索引、API notes 索引、ObjC 元数据归属、按 SDK 版本的磁盘缓存）整体搬进新的独立包 swift-type-indexing，模块名仍是 TypeIndexing。新包不依赖 MachOSwiftSection，也不依赖 MachOObjCSection：原来直接调用 ObjCIndexing 补私有类归属的那一层，改成新包声明的协议 DeclaredTypeNameSource，由 MachOObjCSection 实现。

搬家同时修两处错误：

  • API notes 的改名规则：只有 SwiftPrivate 的类型要加 __ 前缀，有 SwiftName 的直接用它——现在两种都不改名。
  • sourcekitd 只认 Xcode 的目录结构，只装 Command Line Tools 时找不到。

之后三方接入：

  • MachOObjCSection：打印 ObjC 头文件时，按 API notes 在类、协议、category 及其成员上标出 NS_SWIFT_NAME(...) / NS_REFINED_FOR_SWIFT。
  • MachOSwiftSection：删掉 TypeIndexing target，只留一个薄适配层；swift-section interface --resolve-c-module-names 照常可用，swift-section objc 加一个同类开关。
  • RuntimeViewer：在找得到对应平台 SDK 的 Mac 上，默认把 __C.UICellConfigurationState 打印成 UIKit.__UICellConfigurationState。索引在 engine 连上后后台预建、进 Report；建好前先显示 __C.，建好后自动刷新；MCP、命令行与导出一起换成解析后的名字。

详细设计

新包的公开 API 
public protocol DeclaredTypeNameSource: Sendable {
    var imagePath: String { get }
    func declaredTypeNames() async throws -> [String]
}

public enum ImportedTypeNameCategory: Sendable, Hashable {
    case objcClass, objcProtocol, valueType, other
}

public struct TypeIndexingAvailability: Sendable, Hashable {
    public var sdkPath: String?
    public var sourceKitPath: String?        // nil: module interfaces skipped
    public var unavailabilityReason: UnavailabilityReason?
    public static func availability(for platform: SDKPlatform) -> TypeIndexingAvailability
}

public struct SwiftImportAnnotation: Sendable, Hashable {
    public var swiftName: String?
    public var isSwiftPrivate: Bool
}

public enum ObjCMemberKey: Sendable, Hashable {
    case method(selector: String, isClassMethod: Bool)
    case property(name: String, isClassProperty: Bool)
}

public struct ObjCContainerSwiftImportAnnotations: Sendable, Hashable {
    public var declaration: SwiftImportAnnotation?
    public var members: [ObjCMemberKey: SwiftImportAnnotation]
}

@available(macOS 13.0, *)
public actor TypeDatabase {
    public init(platform: SDKPlatform, cacheDirectory: URL? = nil, supplementaryAPINotesURLs: [URL] = [])
    public func index(dependencies: [any DeclaredTypeNameSource], moduleFilter: @Sendable (String) -> Bool) async throws
    public func moduleName(forTypeName typeName: String) async -> String?
    public func swiftName(forCName cName: String, category: ImportedTypeNameCategory) -> String?
    public func swiftImportAnnotations(forObjCClassNamed className: String) -> ObjCContainerSwiftImportAnnotations?
    public func swiftImportAnnotations(forObjCProtocolNamed protocolName: String) -> ObjCContainerSwiftImportAnnotations?
    public static func moduleName(forImagePath imagePath: String) -> String
}

所有源码仍包在 #if os(macOS) 里。协议按「是什么」命名，沿用组织里 ObjCMetadataSource 的 Source 后缀；不给 MachOKit 的类型补遵循新包的协议，由 MachOObjCSection 的包装类型实现。

改名规则 
let swiftName: String? = if let explicitSwiftName = entity.swiftName {
    explicitSwiftName                         // swift_name wins, no "__"
} else if entity.isSwiftPrivate == true {
    "__" + cName                              // swift_private alone
} else {
    nil
}

依据是 Clang importer：有 swift_name 时直接用它并提前返回，只有没有它时才在 swift_private 的声明前加 __。ObjC 成员按同样两条规则记录，但只保存原始的 swiftName / isSwiftPrivate，因为成员一级要打印的是宏。

ModuleIndexCache 的目录改为 <cacheDirectory>/<platform>/<SDK 版本-build>/；不传时是 Application Support/swift-type-indexing/SDKIndexer。旧的 Application Support/MachOSwiftSection/SDKIndexer 不再读、也不自动删，新包第一次运行时重建一次。

MachOSwiftSection：适配层与命令行 
@available(macOS 13.0, *)
public struct TypeDatabaseTypeNameResolver: ModuleNameResolving, CImportedNameResolving {
    public init(typeDatabase: TypeDatabase)
}
  • SwiftInterfaceBuilderTypeNameProvider 保留名字与构造器签名，内部改用这个适配器和 ObjCDeclaredTypeNames。
  • swift-section objc interface --mark-sdk-swift-names：按镜像平台建只读 API notes 的 TypeDatabase（不碰 sourcekitd），为每个类与协议取标注；找不到 SDK 时打印 warning，输出与不加开关时相同。
RuntimeViewer
  • 进程内的索引：RuntimeTypeIndex 每个服务进程一个，每个 SDKPlatform 一个 TypeDatabase。平台按镜像来源取：共享缓存镜像、文件、LC_BUILD_VERSION。Mac Catalyst 用 macOS SDK（读 iOSSupport 里的 API notes，落地时实测确认）。
  • 预建：engine 连上与加载新镜像时，把依赖模块并进过滤条件，同一平台在建时合并请求。不可用时状态记原因，打印器不注册解析器。
  • 打印：每次按当前选项重建完整的解析器列表（opaque + 类型名），不再被 removeAllTypeNameResolvers() 误删；显示与语料两个打印器都这样做。就绪时清 section 的接口缓存，再广播 .typeNamesResolved。
  • 等待：waitsForTypeIndex 为真时，打印前等该平台索引就绪或不可用。MCP、命令行、导出置真，Find 语料构建一律等待；只在磁盘缓存冷的第一次会等。
  • 兼容性：三个新选项都用 @Default；新 case 只由新版 Mac 服务发出；旧对端不回应状态命令时当作不可用。
  • 语料 variant：…-ByCategory-TypeNames<platform>-<SDK 版本-build> 或 …-UnresolvedTypeNames。
  • 界面：Generation Options 的 Swift 组「Resolve Imported Type Names」、ObjC 组「Mark Swift Names From SDK」，默认勾选；Report 新类别「Imported Type Names」，每个平台一行显示建立中、就绪（缓存大小）或不可用（原因）。
  • 内存：每个打印的服务进程各一份，落地时量一次 malloc 在用量写回提案。

调研

二进制里为什么没有 Swift 名与模块
  • Swift 给导入的 ObjC 类做 mangling 时用 ObjC 运行时名（ASTMangler.cpp 的 tryAppendClangName）。UIKit.tbd 里 $s5UIKit24UICellConfigurationStateV19_bridgeToObjectiveCSoABCyF 的 SoABC 直接复用了结构体名那个标识符；PKDrawing、UTType 的符号形状完全相同。
  • 改名只在 SDK 里：UIKit.apinotes 的 SwiftPrivate: true、PencilKit.apinotes 的 SwiftName: PKDrawingReference。
SDK 统计：为什么不能在二进制层面推断
同名又桥接的类型数量例子
__X（SwiftPrivate）6UIKit 的 UICellConfigurationState、UIViewConfigurationState、UIPointerShape……
XReference（SwiftName + SwiftBridge）14PencilKit 8 个、NSDiffableDataSource(Section)Snapshot、UTType、INShortcut
私有框架，SDK 无资料2ASCredentialProvider、WFVariableString

另有 15 个 __ 类型与对应 Swift 类型不同名（如 NSMorphology ↔ Morphology）。

编译器的改名规则与现有实现的偏差
  • ImportName.cpp：有 swift_name 时直接用它并提前返回，不加 __；没有时才对 swift_private 加 __。
  • 现有 APINotesIndex.swift:117 两种都不改名；测试 swiftPrivateEntitiesAreAttributedButNotRenamed 断言了后一种。来历是提案 0009 落地时（2026-08-22）沿用历史实现的保守做法，文档里没有给理由。
sourcekitd 与 Command Line Tools
  • 现有代码拼 <developer dir>/Toolchains/XcodeDefault.xctoolchain/…；Command Line Tools 下 sourcekitd 在 /Library/Developer/CommandLineTools/usr/lib/sourcekitd.framework（本机核对）。
  • Command Line Tools 自带 MacOSX.sdk，含 iOSSupport 的 UIKit.apinotes；iOS 等其他平台的 SDK 只有 Xcode 里有。
  • API notes 不需要 sourcekitd，只有「模块接口里的类型名」这一层需要。
三个仓库的现状要点
  • MachOSwiftSection：12 个文件里 9 个可原样搬走；APINotesIndex、TypeDatabase 要解耦；适配器留下。CImportedTypeNameCategory 打印器自己也用，不能搬。缓存目录写死、调用方无法指定。组织里没有外部使用方。
  • MachOObjCSection：Note 只有 isRefinedForSwift；只有类的入口接收标注；包支持 macOS 10.15 而 TypeDatabase 要求 macOS 13。
  • RuntimeViewer：每个镜像自己的打印器，从未注册类型名解析器；关 opaque 开关会清掉所有解析器；打印都在服务进程；内容区只在对象或选项变化时重取；独立命令行 host 没有 derived data 位置。
  • swift-apinotes 依赖 MetaCodable（宏包，构建时要 swift-syntax）与 Yams；它和 SourceKitD 已经经 MachOSwiftSection 进了 RuntimeViewer 的依赖图。

替代方案

9 条被否的路径
  • 二进制层面推断：同名桥接 20 个里 14 个是 XReference，与 __X 无法区分。
  • 新包留在 MachOSwiftSection：MachOObjCSection 需要同一份数据，却不能反向依赖。
  • 新包继续依赖 ObjCIndexing：ObjC 一侧接入后会成环，改为协议注入。
  • ObjC 一侧另起提案：用户选择一并做。
  • RuntimeViewer 默认关：用户选择找得到 SDK 就自动开。
  • 界面等建好再显示：用户选择先显示 __C.、后台预建、建好刷新。
  • MCP / 命令行 / 导出保持 __C.：用户选择一起换。
  • 开关放 Settings 新分支：要另造一条把设置送进服务进程的通道。
  • 缓存作为 RuntimeDerivedDataKind：derived data 按 dyld 共享缓存分目录，类型索引按 SDK 版本，两者无关。

影响

源码兼容性：MachOSwiftSection 有破坏

  • TypeIndexing product 删除（组织里没有外部使用方），改依赖 swift-type-indexing 或 SwiftTypeNameResolution。
  • SwiftInterfaceBuilderTypeNameProvider 移到 SwiftTypeNameResolution 模块，签名不变。
  • 打开 --resolve-c-module-names 时输出变化：UIKit.__UICellConfigurationState、PencilKit.PKDrawingReference。

MachOObjCSection 为纯新增。四个仓库都以 SPM 源码分发，ABI 不适用。MachOKitUI、SymbolViewer 等其他下游不受影响。

RuntimeViewer 用户能看到的变化

  • Swift 接口里的 __C.X 变成真实模块与 Swift 名；macOS 与 Mac Catalyst 只要装了 Xcode 或 Command Line Tools，其他平台的文件需要装了对应 SDK 的 Xcode。
  • ObjC 头文件出现 NS_SWIFT_NAME(...) / NS_REFINED_FOR_SWIFT。
  • 第一次在某个 SDK 版本上使用时，Report 里有一行「Imported Type Names」在建立；界面先显示 __C.，建好后自动刷新；命令行与 MCP 这期间会等待。
