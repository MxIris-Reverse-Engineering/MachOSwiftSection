摘要

Apple 把一些 Swift 类型从一个模块搬进另一个模块时，会给声明加上 @_originallyDefinedIn(module: "旧模块", 平台 版本)。这个属性让 mangled name 和运行时元数据继续使用旧模块名，老二进制不用重编，所以二进制里只能读到旧名字：CGFloat 现在由 CoreFoundation 声明，mangling 却还是 $s12CoreGraphics7CGFloatV；macOS 15 起 SwiftUI 的约 370 个类型搬进了 SwiftUICore，mangling 还是 7SwiftUI。swift-section interface 因此印出 CoreGraphics.CGFloat、SwiftUI.View，而 SDK 的 .swiftinterface 写的是 CoreFoundation::CGFloat（CoreGraphics 的接口）、SwiftUICore.View（SwiftUI 的接口，2182 处）。

  • swift-type-indexing 在 TypeDatabase 第一次 index 时顺带扫描 SDK 里所有模块的文本 .swiftinterface，把每个顶层类型声明上的 @_originallyDefinedIn 记成「旧模块 + 类型名 → 现在声明它的模块，以及各平台的搬家版本」，新增查询 declaringModuleName(ofMovedTypeNamed:originallyDefinedIn:builtAgainst:)。扫描只读文本，不用 sourcekitd。
  • MachOSwiftSection 的打印器多一个解析器角色 MovedTypeModuleResolving。注册了它，原生 Swift 类型的模块名就先问它，嵌套类型跟随最外层类型。swift-section interface 新增开关 --resolve-moved-type-modules，默认关闭。

是否改写按二进制自己的 SDK 版本判断（LC_BUILD_VERSION 的 sdk）：用 macOS 14 SDK 编出的 SwiftUI 镜像，View 那时还在 SwiftUI 里，照旧印 SwiftUI.View。

要你定

一件事

  1. swift-type-indexing 发 0.2.0 吗？本库的版本下限要等它发版后才能抬到 from: "0.2.0"；在那之前本库只能经本地兄弟依赖构建。

已定（用户批准）

  • 开关做成独立的 --resolve-moved-type-modules，默认关闭。
  • 按二进制的 LC_BUILD_VERSION sdk 判断，不看 minos。
  • dump、diff、snapshot、evolution 不改。
  • TypeDatabaseTypeNameResolver 不变，RuntimeViewer 升级后输出不变。

详细设计

扫描器：只认第 0 列的属性组与紧跟的类型声明 
struct MovedTypeKey: Hashable, Sendable {
    let originalModuleName: String
    let typeName: String
}

struct MovedTypeDeclaration: Hashable, Sendable {
    let typeName: String
    /// The module the mangling names: the part before a `;`.
    let originalModuleName: String
    /// The module whose interface declares the type now.
    let declaringModuleName: String
    let movedVersionsByPlatformName: [String: OperatingSystemVersion]
}

enum MovedTypeIndex {
    static func movedTypeDeclarations(inInterfaceText interfaceText: String, moduleName: String) -> [MovedTypeDeclaration]
}
  • 属性组是连续的、从第 0 列开始的 @ 行；一个属性写多个平台时逐个拆开。
  • 组后第一行去掉属性与修饰词（public、open、final、indirect、nonisolated），关键字是 struct / class / enum / protocol / actor / typealias 才记，名字到 <、:、空格、=、{ 截止，反引号去掉。
  • OSX 视同 macOS，*ApplicationExtension 视同基础平台。
  • module: 有分号取前半段；等于本模块（Swift;CompatibilitySpan）就丢弃。
  • 接口文件：.swiftmodule 目录下 <架构>-apple-<平台后缀>.swiftinterface，排除 .private / .package，按文件名排序取第一个；没有文本接口的模块跳过，读失败记日志跳过。
查询与版本判断：按二进制的 SDK 版本 
extension TypeDatabase {
    public func declaringModuleName(ofMovedTypeNamed typeName: String, originallyDefinedIn originalModuleName: String, builtAgainst sdkVersion: OperatingSystemVersion) -> String?
}
  • 平台条目：macOS → macOS；Catalyst → macCatalyst，没有就 iOS；iOS / 模拟器 → iOS；tvOS、watchOS 同名；visionOS → visionOS，没有就 iOS 并换算（17.x → 1.x，18.x → 2.x，26 起相同，17 以前视为早已搬家）；driverKit 同名。
  • 找不到适用条目：属性在该平台不生效，mangling 本来就是新模块，返回 nil。
  • sdkVersion 不低于搬家版本才返回新模块；未 index 过返回 nil。
  • 用 sdk 不用 minos：mangling 与部署目标无关，interface 要还原的是编译所用 SDK 里的写法；系统镜像的 sdk 就是它所属的系统版本。

已知偏差

属性写的版本不一定是源码真正搬家的时间：CGFloat 写 macOS 10.0，运行时 macOS 13 才搬进 libswiftCoreFoundation。用 macOS 12 SDK 编的二进制也会印 CoreFoundation.CGFloat。这里信属性，不另做修正表。

打印器：新角色与嵌套类型的键 
public protocol MovedTypeModuleResolving: TypeNameResolving {
    func declaringModuleName(ofMovedTypeNamed typeName: String, originallyDefinedIn originalModuleName: String) async -> String?
}

// resolvedModuleName(of:siblingIdentifier:)
if moduleName != objcModule, moduleName != cModule,
   let identifier = siblingIdentifier, !identifier.isEmpty,
   let delegate,
   let declaringModuleName = await delegate.declaringModuleName(ofMovedTypeNamed: identifier, originallyDefinedIn: moduleName) {

  • 返回的 isResolvedCImportedModule 仍是 false，不触发 C 名改写；与 cImportedTypeNameSpelling 无关。
  • declaringModuleForModuleSelector 同时带回模块节点的来源：来自根时带回最外层类型的标识符作键；来自 extension 时不查询。
  • 扩展头：renderExtendedTypeName(_:) 原本对非 C 类型直接照 mangling 印。新增 isMovedTypeReference(_:)，最外层类型被解析器认作搬家时改走类型打印器；没搬家的照旧，输出逐字节不变。

调研

编译器、SDK、现状代码与成本
  1. 编译器：Attr.h:2486 的 OriginallyDefinedInAttr 存 ManglingModuleName 与 LinkerModuleName（"Swift;CompatibilitySpan" 分号前是 mangling 用的模块）。Decl.cpp:1155 的 getAlternateModuleName() 自己没有就沿 DeclContext 往上找，嵌套类型跟随外层。Attr.cpp:2561 的 isActivePlatform 只看平台不看版本。PlatformKindUtils.cpp:131：iOS 条目对 Catalyst 与 visionOS 同样生效。
  2. SDK：libswiftCoreFoundation.tbd 的 $ld$previous 显示 CGFloat 在 macOS 10.15–13.0 位于 libswiftCoreGraphics.dylib，属性却写 macOS 10.0。SwiftUICore 的搬家版本有 15.0、15.2、26.0、27.0 等批次；跟在属性后的声明有 266 struct、23 class、33 enum、40 protocol、5 typealias，另有 994 extension、17 func、185 var、16 let。
  3. 现状代码：NodePrintable.swift:186 的 resolvedModuleName 只对 __C / __ObjC 提问，三个调用点 NodePrintable.swift:176、TypeNodePrintable.swift:197、TypeNodePrintable.swift:310。InterfaceRequest.swift:224 只在 cModuleNameResolution 打开时挂 provider；dump、diff、snapshot、evolution 不挂解析器。import 行来自 SwiftInterfaceBuilder.swift:357 的 collectModules()。
  4. swift-type-indexing（0.1.1）：只回答 __C；sourcekitd 一层不留属性，文档说明不读文本接口。SDKIndexer 已列出每个 .swiftmodule 的路径。
  5. 成本：macOS 27.2 SDK 有 368 个 .swiftmodule、266 份 arm64e-apple-macos.swiftinterface，grep 扫完用时 0.38 秒；Swift 逐行解析的实测落地时补上。
  6. 现在的输出能编过：SE-0491 让 Module::Name 也能找到被该模块重新导出的声明；CoreGraphics 重新导出 CoreFoundation，SwiftUI 的接口第 19 行 @_exported import SwiftUICore。
  7. 使用方：RuntimeViewer 经 TypeDatabaseTypeNameResolver(typeDatabase:) 注册（RuntimeTypeIndex.swift:145），本提案不改它。

替代方案

七条被否的路径
  • 并进 --resolve-c-module-names：那个开关首次要经 sourcekitd 生成接口（UIKit 冷生成 126 秒），名字也说的是 __C。否，两者都开时共用数据库。
  • 从 $ld$previous 推导：给的是库路径不是模块名，还要逐符号归并。否。
  • 经 sourcekitd 接口读属性：只覆盖依赖命中的模块、不留属性，而搬家后的模块常不是直接依赖。否。
  • 不判断版本：macOS 14 的 SwiftUI 会印出当时不存在的 SwiftUICore。否。
  • 按定义是否在被打印镜像里判断：SwiftUICore 镜像会被反着判。否。
  • 打印器协议带版本：版本是镜像的固定属性，构造适配器时给一次即可。否。
  • 给 TypeDatabaseTypeNameResolver 直接加角色：RuntimeViewer 升级后会悄悄改变输出，且拿不到每个镜像的 SDK 版本。否。

影响

纯新增；swift-type-indexing 要先发 0.2.0
  • 源码兼容：纯新增。SwiftInterfaceBuilderTypeNameProvider.init 与 InterfaceRequest 加的参数都有保持现状的默认值；NodePrintableDelegate 是内部协议。
  • ABI：不适用，两个库都以 SPM 源码分发。
  • 下游：swift-type-indexing 0.1.x → 0.2.0 先发版；RuntimeViewer 与 MachOObjCSection 的 ObjCTypeIndexing 不受影响。
  • 非目标：dump；diff / snapshot / evolution 与查找键；import 行；声明在搬过家的 extension 里的嵌套类型；函数与变量的搬家；默认开启；RuntimeViewer 接入。
