摘要

swift-section interface --resolve-c-module-names 能把公开的 C 导入类型写到真实模块下（__C.CGColorRef → CoreGraphics.CGColor），私有的 CF 类型却查不到模块：SDK 里没有它们的头文件，依赖镜像的 Objective-C 元数据也不列 CF 类型，于是按 0106 的规则只印描述符给的裸名（CGSVGDocument）。

本提案在 SwiftTypeNameResolution 里新增 CFDeclaredTypeNames：从镜像的导出表里找出每个 …GetTypeID 函数，列出它定义的 CF 类型（_CGSVGDocumentGetTypeID → CGSVGDocumentRef）。provider 为根镜像登记它；每个直接依赖改登记新的 ImageDeclaredTypeNames，把这个镜像的 Objective-C 名字和 CF 类型合成一个来源，因为 TypeDatabase 每个镜像路径只收一个来源。GetTypeID 只负责定位：一个名字是不是 CF 类型，由根镜像自己的 foreign class 描述符决定。之后 CGSVGDocumentRef 归到 CoreSVG，引用印成 CoreSVG.CGSVGDocument。打印器、swift-type-indexing 和 CLI 参数都不改。

提议方案

  1. CFDeclaredTypeNames：每个 _<名字>GetTypeID 导出给出 <名字>Ref；以下划线开头的私有函数（__LSASNGetTypeID）同时给出去掉前导下划线的拼写。
  2. ImageDeclaredTypeNames：一个镜像的 ObjC 名字在前、CF 名字在后，合成一个来源。分开登记的话，后登记的那个永远读不到。
  3. provider 登记它们：根镜像的 CFDeclaredTypeNames，然后每个直接依赖一个 ImageDeclaredTypeNames。GetTypeID 只负责定位，「是不是 CF 类型」由 foreign 描述符决定：CF 来源只给出根镜像的 foreign class 描述符证实的名字。
  4. 打印器、swift-type-indexing、CLI 参数都不改，只补帮助文字和 skill 说明。

非目标

  • 跟着重新导出找子框架（LSASNRef → CoreServices），与 ObjC 来源一起另开提案。
  • 间接依赖（CFPhoneNumberRef）：放宽到传递闭包会让 SourceKit 接口生成回到几百个模块。
  • 没有 GetTypeID 导出的类型；自己定义、不导出 GetTypeID 的 CF 桥接类型印裸名（测试里的 ProbeLonelyRef）。
  • 本镜像没有描述符的引用：闸门挡在外面，仍印 __C.XRef。
  • 根镜像自己的 ObjC 类、dump、RuntimeViewer 接入（发版后把 ObjCDeclaredTypeNames 换成 ImageDeclaredTypeNames）。
  • 模块名与它里面的类型同名时（IOSurface.IOSurface 编不过）改用模块选择器 IOSurface::…：打印器的通用拼写问题，另做。

详细设计

API 
public struct CFDeclaredTypeNames<MachO: MachORepresentable & Sendable>: DeclaredTypeNameSource {
    public let imagePath: String
    public init(machO: MachO, imagePath: String)
    init(machO: MachO, imagePath: String, restrictedTo admittedTypedefNames: Set<String>?)   // internal
    public func declaredTypeNames() async -> [String]
}

public struct ImageDeclaredTypeNames<MachO: ObjCMetadataSource>: DeclaredTypeNameSource {
    public let imagePath: String
    public init(machO: MachO, imagePath: String)
    init(machO: MachO, imagePath: String, restrictingCFTypesTo admittedTypedefNames: Set<String>?)   // internal
    public func declaredTypeNames() async throws -> [String]
}

extension SwiftInterfaceBuilderTypeNameProvider {
    static func declaredTypeNameSources(root: MachO, dependencies: [MachO]) -> [any DeclaredTypeNameSource]
    static func cfTypedefNames(referencedBy image: MachO) -> Set<String>
}

判定 CF 类只看描述符：种类是 class、isCImportedContextDescriptor 为真、import info 的 isCTypedef 为真且不是相关实体。只有 CF 类型会被升格成 class 而又来自 C typedef。名字取 ABI 名，ClangImporter 保留了 C 拼写时（IOSurfaceRef）取描述符自己的名字。带闸门的构造器是 internal，公开接口不变。

命名规则
  1. 导出名以一个 _ 开头，去掉它得到 C 函数名。
  2. C 函数名以 GetTypeID 结尾，去掉后缀的部分是合法 C 标识符且不全是下划线，记为 base。
  3. 给出 base + "Ref"；base 以下划线开头时再给出去掉前导下划线的拼写。
  4. 规则会产生 CFRef 这类非类型名字；provider 登记的来源都带闸门，只留根镜像证实的名字。

调研

十条查证过的事实
  1. CF 类导入成 ForeignKind::CFType 的类并合成 _CFObject；描述符种类 class，import info 写着 N<typedef 名> 与 St。
  2. 模块不在二进制里；Swift 取顶层 Clang 模块。
  3. GetTypeID 的镜像就是模块：46 个公开 CF 类全部一致。
  4. 打印器在模块解析出来以后已经会用描述符的名字。
  5. swift-type-indexing 已有 DeclaredTypeNameSource 注册表；TypeDatabase 按镜像路径去重，同一路径的第二个来源被丢掉（实现时由端到端测试发现）。
  6. 去 Ref 规则只认 SDK 里有的名字，私有类型走描述符名（AGGraphRef → Graph）。
  7. provider 只读直接依赖；RuntimeViewer 自己给每个镜像登记来源。
  8. 按设计 20 个里覆盖 15 个；实测覆盖更多（有描述符但没有一致性记录的也算上）。
  9. 带 Ref 的拼写在 Swift 里不能用；IOSurfaceRef 因为和 ObjC 类 IOSurface 重名而保留 Ref。
  10. IOSurfaceRef 疑似问题未复现：TextRecognition 印 CoreGraphics.IOSurfaceRef，能编过；IOSurface.IOSurfaceRef 因模块名被同名类遮住编不过，要写 IOSurface::IOSurfaceRef。

替代方案

七条被否或推迟的方向
  1. 打印器上另注册一个 ModuleNameResolving：否，注册表已经在 swift-type-indexing。
  2. 让 swift-type-indexing 自己读导出表：否，那个包按设计不读 Mach-O。
  3. 从 CF 运行时类注册取名字：否，要反汇编调用点，结果与导出表等价。
  4. 用一致性符号里的模块：否，那是声明一致性的模块。
  5. 让去 Ref 规则也认运行时名表：否，会改错 IOSurfaceRef 与 Graph。
  6. 跟着重新导出算进伞框架：推迟。
  7. 让 swift-type-indexing 允许一个镜像路径登记多个来源：否，本提案不改那个包。

影响

  • 源码兼容性：纯新增两个公开类型，provider 的公开接口不变；--resolve-c-module-names 下私有 CF 类型带上模块。
  • ABI：不适用，SPM 源码分发。
  • 下游：InterfaceRequest 自动受益；RuntimeViewer 发版后把 ObjCDeclaredTypeNames 换成 ImageDeclaredTypeNames 才受益。
  • API 演进：没有被替代的旧 API，按 minor 版本发布。
