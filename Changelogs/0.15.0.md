# 0.15.0

A packaging release. No rendering or parsing behavior changes: this one moves two things out of the package so that MachOObjCSection can finally use them, and moves one thing in so that it sits next to the metadata it describes.

1. **`MachOExtensions` is gone from this package** — it now ships as the standalone [MachOKitExtensions](https://github.com/MxIris-Reverse-Engineering/MachOKitExtensions). This package depends on it exactly as before, so `import MachOKitExtensions` is the only source-level difference; the rename is because it extends MachOKit, not a module named MachO.
2. **The `OutputTransformer` product is gone** — its five Swift comment modules ship as the new `SwiftOutputTransformer` product from this package, while the shared `Transformer` namespace and `Module` protocol stay in swift-semantic-string. `Transformer.SwiftEnumLayout` and friends still spell the same.
3. **Twenty redundant imports removed** — `MachOFoundation` already re-exports `MachOKitExtensions`, so nothing above that line needed to import it.
4. **Dependencies move up** — MachOObjCSection to `0.8.102` (the release carrying its new rendering products) and MachOKit to `0.52.100`, which `0.8.102` requires.

Rendered output is byte-for-byte unchanged.

## Highlights

### `MachOKitExtensions` — breaking a package-level cycle

The `MachOExtensions` target held the shared MachOKit groundwork: address arithmetic, pointer-tag stripping, dyld shared cache resolution, bind/rebase, and typed load-command accessors. It could not be shared with MachOObjCSection, because this package already depends on MachOObjCSection — depending back would have formed a package-level cycle. MachOObjCSection said so in a comment on `MachOObjCSectionRepresentable`, and traded away the `cache` / `identifier` requirements to stay cycle-free.

Standing the target up as its own package removes the constraint: both packages depend on `MachOKitExtensions`, neither on the other. That is what makes MachOObjCSection's new rendering layers possible.

Two things were settled during the extraction:

- **The 65 `package`-level symbols are now `public`.** Their callers are across a package boundary, so there was no incremental option.
- **The Apple-only `FrameworkToolbox` dependency is dropped**, because MachOObjCSection supports Linux and inheriting an Apple-only dependency would have regressed that. It was used in exactly three places, all rewritten against the standard library. The two spellings it offered are not interchangeable — `.box.int` converts by value and traps on overflow, `.box.bitPattern.int` reinterprets the bits — and all three sites were the latter. `@AssociatedObject` is kept: it routes through swift-object-association off Apple platforms, and its C helper only uses `__builtin_return_address`.

One source change was unavoidable on this side: `MachOReading/Readable/UnsafeRawPointer+Readable.swift` used `box` while relying on the in-package target to drag `FoundationToolbox` along. With the target external and deliberately Apple-free, that import is spelled out.

### `SwiftOutputTransformer` — the comment templates move next to their subject

The transformer modules turn a rendered comment into a user-editable token template (`${startOffset}`, `${bitsNeededForTag}`, …). They used to live entirely in swift-semantic-string. Their tokens, though, are Swift runtime metadata vocabulary — `payloadRegionBytesHex` means nothing to a general-purpose string package — so the five Swift modules and `Transformer.SwiftConfiguration` move here, and the ObjC ones (`CType`, `ObjCIvarOffset`) move to MachOObjCSection.

What stays shared in swift-semantic-string is the `Transformer` namespace and the `Module` protocol. That part is deliberate rather than incidental: if each side declared its own `Transformer` enum, a consumer importing both — RuntimeViewer's settings UI does — would have to qualify every reference. Extending one shared namespace keeps `Transformer.CType` and `Transformer.SwiftEnumLayout` unqualified and side by side.

### Import hygiene

`MachOFoundation/Exported.swift` re-exports `MachOKitExtensions`, and `MachOSwiftSection` re-exports `MachOFoundation` in turn, so every target above that line already sees the symbols. Twenty imports carried over from when the target lived inside this package are removed.

Targets at or below `MachOFoundation` keep theirs — they cannot reach through it without forming a cycle. So does `swift-section`'s `IgnoreCoding.swift`, which imports nothing else and therefore has no re-export to ride on. Three target dependency entries that no longer back any import are dropped as well.

## Compatibility

**Two product-level removals.** Both have direct replacements:

| Removed | Replacement |
|---|---|
| `MachOExtensions` (target) | `MachOKitExtensions` package — add it as a package dependency and `import MachOKitExtensions` |
| `OutputTransformer` (product of this package) | `SwiftOutputTransformer` (this package) for the Swift modules; swift-semantic-string's `OutputTransformer` for the namespace and protocol |

No type was renamed and no API signature changed — `Transformer.SwiftFieldOffset`, `MachORepresentableWithCache`, `address(forOffset:)` and the rest are spelled exactly as before. Only the module they arrive from differs.

**Pinned dependencies** for this release:

- `MachOKit` → `exact: "0.52.100"`. The previous `0.51.101` pin had quietly fallen behind: MachOObjCSection has required `0.52.100+` since its `0.8.x` line, but the referenced `0.7.103` only asked for `0.46.100+`, so the conflict never surfaced. Local builds resolved MachOKit through a sibling checkout at `0.52.100` all along, so the source has been building against it — only the pin lagged.
- `MachOObjCSection` → `exact: "0.8.102"`.
- `MachOKitExtensions` → `from: "0.1.0"`.
- `swift-semantic-string` → `from: "0.3.0"`.
- `swift-demangling` → `0.4.5 ..< 0.5.0`, unchanged and for the reasons given in `0.14.1`.

## Testing and CI

- New `SwiftOutputTransformerTests` covers the five Swift modules and `SwiftConfiguration`, including missing-key-tolerant decoding, so stored configurations from earlier versions still load.
- The transformer tests that used to live in swift-semantic-string are split along the same line as the modules: the Swift ones here, the ObjC ones in MachOObjCSection, and the aggregate `Transformer.Configuration` with RuntimeViewer, its only consumer.
