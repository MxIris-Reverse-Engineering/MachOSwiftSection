摘要

六个 MachO 系列包里有五个已经在 Swift 6 语言模式下编译，complete strict concurrency checking 早已按错误执行；唯一的例外是 MachOKit（fork），它的清单还是 swift-tools-version: 5.10。本提案做两件事：把 MachOKit 升到 tools 6.2，让它也进入 Swift 6 语言模式（实测零错误，Sources 里零并发诊断）；然后在六个包的每个 Swift target 上开启 ExistentialAny、MemberImportVisibility、InferIsolatedConformances 三项 upcoming feature（编译器把它们标为 Swift 7 默认开启），开关在每份清单末尾用一个循环统一加，不逐个 target 写。

源码改动约 900 处，绝大部分是补 import 与补 any；非测试 target 用 swift package migrate 自动改，测试 target 照诊断清单手改，另有 6 处工具处理不了、要先手工改好。同为 Swift 7 默认的 NonisolatedNonsendingByDefault、InternalImportsByDefault、ImmutableWeakCaptures，以及独立的 StrictMemorySafety，量过之后明确不做。

提议方案与非目标

  1. MachOKit 进 Swift 6 语言模式。第 1 行改成 // swift-tools-version: 6.2，tools 6.x 不声明 swiftLanguageModes 时默认 Swift 6。删掉九项 Swift 6 已默认开启的 upcoming setting 与 CaseIterable 扩展，改用统一开关；AccessLevelOnImport 实验特性保留，编译器提示多余再删。
  2. 六个包的每个 Swift target 统一开启三项特性。每份清单在 let package = Package(...) 之后加一个循环，给除 system、binary、plugin 以外的所有 target 追加同一组设置；本库沿用 Package.swift:1541 已有的常量。test、macro、executable target 都包括在内。
  3. 源码按三类处理。先手工改好 6 处预修；再对非测试 target 跑 swift package migrate（改清单那步报错是预期的，以「Applied N fix-its」为准）；测试 target 用 --build-tests 加三个 :migrate 开关构建，照警告逐条手改。最后才加清单里的开关，正式开启后确认零错误。
  4. 每加一条 import Semantic，就检查那个文件里裸写的 Error、Numeric、Argument。类型位置写 Swift.Error / Swift.Numeric；as Error、is Error 与 catch 模式逐个看；「cast always fails」警告按错误对待。
  5. 从下往上落地，不为此单独发版。MachOKit → swift-semantic-string → swift-demangling → MachOKitExtensions → MachOObjCSection → 本库。设置只影响包自身的编译，不改公开 API。

非目标

  • 不开 NonisolatedNonsendingByDefault、InternalImportsByDefault、ImmutableWeakCaptures、StrictMemorySafety。
  • 不动 FrameworkToolbox（不属于 MachO 系列）。
  • 不给 swift-semantic-string 的 Error、Numeric、Argument 改名（公开 API 破坏）。
  • 不清理现有的 @unchecked Sendable（本库 84 处）与 nonisolated(unsafe)（37 处）：大多是锁保护的状态，macOS 10.15 用不了 Mutex。
  • 不采用 typed throws、~Copyable、Span 等新语言特性。
  • 不把这些改动提给上游 p-x9/MachOKit。

详细设计

统一开关（五个兄弟包写在清单末尾） 
let upcomingFeatureSettings: [SwiftSetting] = [
    .enableUpcomingFeature("ExistentialAny"),
    .enableUpcomingFeature("MemberImportVisibility"),
    .enableUpcomingFeature("InferIsolatedConformances"),
]

for target in package.targets where target.type != .system && target.type != .binary && target.type != .plugin {
    target.swiftSettings = (target.swiftSettings ?? []) + upcomingFeatureSettings
}

本库写在 extension SwiftSetting（Package.swift:1541）之后、Tuist 块（:1550）之前，数组里用已有的 .existentialAny、.memberImportVisibility、.inferIsolatedConformances；另外三个未用的常量留着，将来开时直接加进数组。

MachOKit 清单

第 1 行改为 // swift-tools-version: 6.2；MachOKit target 的 swiftSettings 只剩 .enableExperimentalFeature("AccessLevelOnImport", .when(configuration: .debug))；原来的 extension SwiftSetting { static let forwardTrailingClosures … } 与 extension SwiftSetting: @retroactive CaseIterable 整段删除；末尾加与兄弟包相同的循环。

MachOKit 进 Swift 6 模式

Swift 5 模式加 -strict-concurrency=complete：Sources 零并发诊断，Tests 3 条警告。直接 -swift-version 6（从构建数据库核实四个 target 都拿到了）：全部编过、零错误。上游 p-x9/MachOKit 同样是 tools 5.10；fork 比上游多 35 个提交、少 40 个。

swift package migrate 的实际表现与迁移模式的坑
  • 非测试 target：258 个文件里套用了 300 个 fix-it（+304 / −57），然后在改清单那一步失败（unable to find target named 'Utilities' in package），源码已经改好。
  • 测试 target：一处都不改，显式 --target 也是 Applied 0 fix-its。
  • 构建一失败就一处都不改。本库 4 处在迁移模式下直接报错：TypeAttributeInferrer.swift:143（switch must be exhaustive）、ABIDiffer.swift:289（.enum 解析成实例成员）、两个测试文件的 .values 落到 dynamic member lookup。
  • swift-semantic-string 公开声明了 struct Error、struct Numeric、Argument。文件直接 import Semantic 后裸写的 Error 解析成 Semantic.Error：ObjCAPIRequests.swift:295 与 ABIEvolutionRequest.swift:180 因此编不过；as Error 一类转型则不报错、只变成永远失败。
  • 补完 6 处、migrate 跑完、清单手加开关后，Sources 全部编过；测试 target 逐个报缺 import，与警告清单一致。
  • 清单里给 C target 加 swiftSettings 无害：同一个循环在六个包上都照常编过。

替代方案

六条，都否了或改了形状
  • MachOKit 只加 StrictConcurrency：Swift 5 模式下只是警告，约束力不够。
  • MachOKit 用 swiftLanguageVersions: [.version("6")]：tools 6 已废弃改名，写法与兄弟包不一致，第 1 行的上游冲突也省不掉。
  • 逐个 target 写或让 migrate 改清单：本库 53 个 target、MachOKitExtensions 24 个、MachOObjCSection 19 个，容易漏；migrate 在本库清单上直接失败。选统一循环。
  • 四项全开：调研结果摆出来之后，用户选了只开三项低风险的。
  • 不开 MemberImportVisibility：它改动最大、坑最多，但正是「依赖写在自己的 import 里」的来源，坑也都已找全。保留。
  • 给 Semantic.Error 改名：公开 API 破坏，不在本次范围；只在调用点写 Swift.Error。

影响

  • 源码兼容性：纯新增。六个包都不改任何公开声明的签名；MachOKit 换语言模式不改变公开 API。upcoming feature 只作用于开启它的 target 本身，不传给下游。
  • ABI：不适用，SPM 源码分发。
  • 下游：RuntimeViewer、MachOKitUI、SymbolViewer 不用改代码；RuntimeViewer 与本库的 Tuist workspace 重新生成后带上新设置，最后一步编一遍确认。上游 p-x9/MachOKit 不提交，合上游 tag 时清单两处会冲突，按 fork 写法解决。
  • 文档：账本加一节、索引登记；CLAUDE.md 预计不加条目（编译器会当场指出漏写），落地时再判断。
  • API 演进：没有废弃的 API，不需要 major 跃迁，不单独发版。
