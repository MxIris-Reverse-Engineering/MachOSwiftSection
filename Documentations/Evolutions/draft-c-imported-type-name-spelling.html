摘要

Swift interface 里，从 C 导入、被改了名的类型（NS_SWIFT_NAME、typedef、CF 的 Ref 去尾）现在声明行印 Swift 名、其余地方印 C 名：struct AnyWeakAttribute { var _details: __C.AGWeakAttribute.__Unnamed_struct__details }，紧跟着 extension __C.AGWeakAttribute: Swift.Hashable {}。原因是声明行取类型描述符里的名字，而引用处取 mangled 名，Swift 给 Clang 声明做 mangling 时一律用 C 名。描述符的导入信息（import info）里两个名字本来都存着，不需要 SDK。

本提案让打印器多一个拼写选项 CImportedTypeNameSpelling：

  • 默认 .swiftName：声明、成员类型、扩展头全部用 Swift 名。查不到所属模块时写裸名（extension AnyWeakAttribute: Swift.Hashable {}），查得到时照旧写成 模块.Swift名。
  • .cName：一律按 mangled 的样子印（声明 struct AGWeakAttribute，引用 __C.AGWeakAttribute）。

同时修掉扩展头不经类型名解析器的问题：SDK 类型的成员已经解析成 CoreFoundation.CGRect，扩展头却还是 __C.CGRect。

RuntimeViewer 把这个选项做成全局生成选项（Generation Options › Imported Type Names: Swift / C）。用 SourceEditor 显示时，改了名的 C 类型在声明行末尾带一条 Xcode 式的行尾标注（Imported from C as AGWeakAttribute），点开后用里面的按钮切换。

要你定

已定：两次点击

用户批准按 Xcode 原生的两步做：点横幅弹出下拉框，用里面的按钮切换；右键横幅的菜单里也有同一个动作。不改 Mx-Iris/SourceEditor。

方案

MachOSwiftSection

  1. 拼写选项：SwiftDeclarationPrintConfiguration.cImportedTypeNameSpelling，默认 .swiftName。
  2. 本镜像的名字表：打印器第一次需要时，从本镜像所有 C 导入的类型描述符建一张表，以 mangled 身份为键、描述符的名字为值，只收可信的条目：
    • 有 ABI 名，且与描述符的名字不同；
    • 不是相关实体（__C_Synthesized 里的错误码结构体之类）；
    • ABI 名不以描述符的名字结尾——导入成成员的类型（NSAttributedStringKey → Key）都长这样，描述符给的只是叶子，宁可不改名。代价是 NSDecimal → Decimal 这类顶层改名也被挡掉，照旧印 C 名，有 SDK 时由类型索引补上。
  3. .swiftName 下一个 __C 引用怎么印（按顺序取第一个成立的）：解析器把模块解析出来了 → 照旧 模块.Swift拼写；名字表里有它 → 只写 Swift 名，不写模块（AnyWeakAttribute）；都没有 → 照旧 __C.ABI名。嵌在 C 类型里的类型，父类型那一段按同样的规则印（AnyWeakAttribute.__Unnamed_struct__details）。
  4. .cName：引用一律按 mangled 的样子印 __C.ABI名，不问任何解析器——模块也不解析，因为 UIKit.UICellConfigurationState 会和同名的 Swift 结构体混淆。
  5. 声明行与引用走同一套规则：.cName 下是 ABI 名；.swiftName 下依次取解析器给的 Swift 拼写（可以带点号，struct NSAttributedString.Key）、名字表里的名字、ABI 名。不可信的条目因此从 struct Key 变成 struct NSAttributedStringKey。
  6. 扩展头改走异步的类型打印路径：只改扩展类型根在 __C / __C_Synthesized 的扩展，仍包成同一种 TypeDeclaration。其余扩展一个字节都不变。
  7. 标注：marksCImportedTypeNames（默认关）打开时，两种拼写不同的声明名外面包一个 AnnotationRegion，kind 里带着两个名字。文本不变，分离之后与不标注时逐字节相同。
  8. swift-section interface --c-imported-type-name-spelling swift-name|c-name，默认 swift-name。

RuntimeViewer

  1. 生成选项：SwiftGenerationOptions.cImportedTypeNameSpelling（@Default(.swiftName)）。面板的 Swift 一组加一行 Imported Type Names: Swift | C。它与「Resolve Imported Type Names」各管各的：后者在 C 名模式下不起作用，也不再为它建类型索引。
  2. 内部标注开关：GenerationOptions.marksCImportedTypeNames，不出现在面板里，存下来的值永远是 false；内容区只在 SourceEditor 可用时打开，currentMergedGenerationOptions 照同样的规则合并。
  3. 接口带回名字：RuntimeObjectInterface.cImportedTypeNames，每条是声明名的 UTF-8 范围和两个名字，与宏展开在同一处从标注区域里取出；注释结构不认这种 kind。
  4. 行尾标注：bridge 新增 showLineAnnotations(_:) 与一个代理回调。Swift 名模式写 Imported from C as AGWeakAttribute / Show C Names，C 名模式写 Imported to Swift as AnyWeakAttribute / Show Swift Names。切换就是翻转全局生成选项，所有内容区一起重新取接口。
  5. 其余出口跟着选项走：MCP、App 充当 host 时的命令行、导出读的都是 appDefaults.options；独立运行的命令行 host 用默认的 Swift 名。Find 语料始终用 Swift 名打印。

非目标

  • 不推断导入成成员的类型的父路径：描述符只给叶子，没有 SDK 就保持 C 名。
  • 相关实体（__C_Synthesized）不改。
  • 只在声明行放提示，引用处不放。
  • 侧栏、路径栏、Find 结果里的对象名不跟着切换；Find 语料始终是 Swift 名，搜 C 名搜不到改了名的引用。
  • dump、diff、snapshot 的键不变（ABI diff 按 mangled 身份对比）。
  • NSTextView 显示路径与 iOS 版不放提示；命令行工具不加对应参数。

详细设计

一个 __C 引用怎么印 
printType(reference rooted in __C)
├─ spelling == .cName                       -> "__C." + ABI name       (no resolver asked)
└─ spelling == .swiftName
   ├─ a resolver resolves the module        -> Module + Swift spelling (existing path)
   ├─ name table has a trusted entry        -> bare Swift name          AnyWeakAttribute
   └─ otherwise                             -> "__C." + ABI name        __C.NSAttributedStringKey

declared name of a C-imported descriptor
├─ .cName                                   -> ABI name                 AGWeakAttribute
└─ .swiftName                               -> resolver's spelling ?? trusted name ?? ABI name
MachOSwiftSection 的公开 API 
public enum CImportedTypeNameSpelling: String, Sendable, Hashable, CaseIterable {
    case swiftName
    case cName
}

// SwiftDeclarationPrintConfiguration
public var cImportedTypeNameSpelling: CImportedTypeNameSpelling = .swiftName
public var marksCImportedTypeNames: Bool = false

public struct CImportedTypeNames: Sendable, Hashable {
    public let swiftName: String
    public let cName: String
    public init(swiftName: String, cName: String)
}

extension AnnotationRegion.Kind {
    public static func cImportedTypeName(_ names: CImportedTypeNames) -> Self
    public var cImportedTypeNames: CImportedTypeNames? { get }
}

kind 的编码是 "cImportedTypeName" + "\u{1F}" + swiftName + "\u{1F}" + cName；U+001F 不会出现在标识符里，Swift 名里可以照常带点号。

名字表与可信规则（模块内部） 
struct CImportedTypeSwiftNameTable: Sendable {
    init(typeContextDescriptors: [TypeContextDescriptorWrapper], in context: some ReadingContext)
    func swiftName(forIdentity identity: Node) -> String?

    static func trustsUserFacingName(_ userFacingName: String, importInfo: TypeImportInfo) -> Bool {
        guard let abiName = importInfo.abiName, abiName != userFacingName, !importInfo.isRelatedEntity else { return false }
        return !abiName.hasSuffix(userFacingName)
    }
}
  • 键是 mangled 身份节点（SymbolicDemangler.demangleContext(for:in:)）的结构，照 ExtensionName 的结构化 Hashable。
  • 只遍历 C 导入的描述符，读名字与 typeImportInfo(in:)；第一次需要时才建，配置怎么变都不重建；读出错的条目跳过。
打印规则的落点
  • printType(_:)：.cName 写原模块名与标识符；.swiftName 先走现有路径，模块没解析出来但名字表有答案时，不写模块与分隔符，把 Swift 名写成标识符（语义仍是这个类型的 printIdentifier 上下文，跳转不受影响）。嵌套类型的父段递归回 printType，套用同一规则。
  • printModuleSelector(ofNestedType:)：父段是改了名的裸名时不写模块选择器。
  • renderTypeDeclarationHeader：C 导入的描述符按方案第 5 条取名；解析器那一路用 ABI 名去问，与引用处的查询相同，声明与引用必然一致。displayParentName == true 那条路不变。
  • renderExtendedTypeName 改成 async：根在 __C 时走 typeDemangleResolver.resolve(for:) 再 .replacingTypeNameOrOtherToTypeDeclaration()；其余分支原样。

调研

11 条查证过的事实
  1. 复现：swift-section 0.24.0 interface --show-c-imported-types 打 macOS 27.2 的 AttributeGraph，得到 struct AnyAttribute、struct AnyWeakAttribute { … var _details: __C.AGWeakAttribute.__Unnamed_struct__details } 与 struct WeakAttribute<A> { var base: __C.AGWeakAttribute }。
  2. 两套名字从哪来：声明行取 descriptor.name(in:)（SwiftDeclarationPrinter+Headers.swift:47/56/73）；引用来自 mangled 名，Swift 按 Clang 名 mangling（ASTMangler::tryAppendClangName），SymbolicDemangler.cImportedTypeIdentity（SymbolicDemangler.swift:982）是反方向的映射。
  3. 描述符里存的是什么：IRGen computeIdentity（GenMeta.cpp:1568）写的是 Swift 名的叶子，名字不同时追加 N<ABI 名>。shared cache 实测：AnyAttribute/AGAttribute ×9、AnyWeakAttribute/AGWeakAttribute ×4、CGColor/CGColorRef ×142、Decimal/NSDecimal ×47、Key/NSAttributedStringKey ×158、Name/NSNotificationName ×68。导入成成员的类型只剩叶子。
  4. 父上下文：getAddrOfParentContextDescriptor（GenDecl.cpp:885）把 Clang 导入的名义类型一律挂到 __C 下，父路径不在二进制里。
  5. 现有改名的条件：printType（TypeNodePrintable.swift:170-262）只在模块解析成功后才改标识符。
  6. 扩展头不经解析器（读代码得出，未实测）：renderExtendedTypeName 调同步的 ExtensionName.print，四个调用点。
  7. 可用的 API：machO.swift.typeContextDescriptors、isCImportedContextDescriptor(in:)、typeImportInfo(in:)、SymbolicDemangler.demangleContext(for:in:)；打印器已有按需建一次的状态写法。
  8. 标注区域只有 kind 和内容；名字编进 kind 有先例（attachedMacroTrackedProperty(_:named:)）。
  9. 命令行：InterfaceCommand.swift、InterfaceRequest.swift；插件 skill §8，清单 0.27.0。
  10. RuntimeViewer：生成选项在 appDefaults.options，内容区随它重取；面板有 .enumOption；注释结构与宏展开都是「标区域 → 分离 → 接口带可选字段」；bridge 是 Objective-C 协议，从未用过行尾标注；命令行插件 1.4.0 尚未发布。
  11. 复刻版 SourceEditor 的行尾标注（tag 27.2.0-alpha.2）：insertLineAnnotation(_:) 等公开入口齐全；横幅本身不带按钮，点横幅弹下拉框（handleLeftMouseUpEvent），右键菜单只有 revealAction；交互代理没有「点了横幅」的回调。

替代方案

6 条被否的路径
  • 模块未知时写 __C.AnyWeakAttribute：与声明行仍不一致，且是打印器以前特意避开的半翻译写法；用户选了裸名。
  • 默认按 C 名统一：读的是 Swift interface，Swift 名更贴合；C 名作为可切换的拼写保留。
  • 按前缀推断成员导入的父类型：二进制里没有父路径，前缀切分会切出 NS.Decimal 这种错误结果。
  • 类型名后面的胶囊标签：要多输出一段注释，复制与导出会带上它，还要给标签加点击；用户选了行尾标注。
  • 只切换当前编辑栏：要另存一份不进设置的状态，缓存键多一维；用户选了全局生成选项。
  • 拼写与 resolvesImportedTypeNames 合成三档：类型索引功能还在验收，合并就要改它的设置与测试；两个开关各管各的更简单。

影响

源码兼容性

  • 纯新增：两个类型、两个配置属性、kind 的构造与解析。renderExtendedTypeName 是 package，改 async 只影响本包四处调用。
  • 输出有变化：改了名的 C 类型的引用与扩展头变成 Swift 名；不可信条目的声明行从叶子名变成 C 名（struct Key → struct NSAttributedStringKey、struct Decimal → struct NSDecimal）；注册了解析器时 SDK 类型的扩展头变成 模块.名字。

ABI 兼容性

不适用 —— 本库以 SPM 源码分发，使用方每次重新编译。

下游影响

  • 本仓库：SwiftInterfaceBuilder、diff --interface 的渲染、swift-section interface 的默认输出跟着变；ABI diff 的键不变。
  • MachOKitUI、SymbolViewer：输出变化同上，不需要改代码。
  • RuntimeViewer · 用户可见：SourceEditor 下改了名的声明行末尾多一条灰色行尾标注；Generation Options 多一行；默认接口统一成 Swift 名；MCP、App 充当 host 时的命令行与导出跟着选项；Find 结果始终是 Swift 名。
  • RuntimeViewer · 兼容：旧设置取 .swiftName，标注开关存下来永远是 false，不需要迁移；提示只在 macOS 的 SourceEditor 路径；不涉及权限、公证与 Sparkle；Find 语料的旧文件因产出者身份改变自然失效，不必改 variant。
  • 顺序约束：两边都叠在 swift-type-indexing-package 上（它还在两个仓库的本地 next、没推送），要等它先收尾，或在它的功能分支之上开分支。
