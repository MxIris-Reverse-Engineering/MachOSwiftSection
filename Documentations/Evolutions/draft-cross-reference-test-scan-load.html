摘要

CrossReferenceAnalysisTests 里有四个测试辅助函数用不设上限的 DispatchQueue.concurrentPerform 扫描整份 dyld shared cache，Debug 构建下每次跑测试都把机器的全部核心占满好几分钟。本提案做两件事：

  1. 测试限并发：新增全进程共用的扫描名额 ImageScanConcurrency，默认 max(2, 核心数 / 2)，四处扫描改走它；Swift Testing 并行跑多个套件时，所有扫描加起来也不超过名额。另加源码扫描测试，禁止以后绕过它直接调 concurrentPerform。
  2. Debug 提速：Tuist 开发工作区里，让 MachOCodeReferences、ARM64InstructionDecoding 在 Debug 配置下也用 -O 编译，去掉每条指令一次的 Swift 运行时元数据查找。

库的公开 API、原生 MachOSwiftSection.xcworkspace、swift test 与 CI 的行为都不变。

要你定

已批准并实现；剩一个后续问题

  1. 开头约 35 秒仍会用满核心，那是 Swift Testing 同时跑着二十多个测试，不在本提案范围。要不要另外限制测试运行器的并行度？

实测结果（Ultra，Debug，-only-testing:CrossReferenceAnalysisTests）

  • 耗时：约 14 分钟 → 约 1.5 分钟；xctest 累计 CPU 时间：约 234 分钟 → 约 14 分钟（约 17 倍）。
  • 四处扫描同时占用的线程不超过名额（采样最多 8 个，名额 14）；开头约 35 秒的满核来自 Swift Testing 自身的并行。
  • Tuist 的 base 设置盖得过按配置写的 -Onone，后备写法没用上。

改了什么：四处调用点改走共用名额；Tuist 清单给两个扫描模块在 Debug 下开 -O。

名额在并行的套件之间共用：每次调用最多起「名额」个工作者，每扫一个镜像先取一个名额。

Debug 下热路径为什么慢：未特化的区间循环每走一步都查一次元组元数据，28 个线程争同一把锁。

详细设计

ImageScanConcurrency 
enum ImageScanConcurrency {
    static let maximumConcurrentScans = max(2, ProcessInfo.processInfo.activeProcessorCount / 2)

    private static let permits = DispatchSemaphore(value: maximumConcurrentScans)

    static func concurrentPerform(iterations: Int, execute body: (Int) -> Void) {
        guard iterations > 0 else { return }
        let cursor = IterationCursor(iterationCount: iterations)
        DispatchQueue.concurrentPerform(iterations: min(maximumConcurrentScans, iterations)) { _ in
            while let index = cursor.next() {
                permits.wait()
                defer { permits.signal() }
                body(index)
            }
        }
    }
}
  • 每次调用也限工作者数：只靠信号量的话，多出来的线程全阻塞在 permits.wait() 上，workqueue 还会补新线程；先限工作者数，阻塞线程就有上界。
  • 不会卡死：名额只在扫一个镜像期间持有，扫描是同步 CPU 工作，不等线程池；调用线程即便是 cooperative thread，等的也是不需要池线程的扫描线程归还名额。嵌套调用会卡死，文档注释写明禁止。
  • CI：3 核 runner 上 3 / 2 = 1，取下限 2。

怎么量
  • 同机没有别的测试在跑时量，TUIST_SCRIPT_ROOT 用 agent 专属目录。
  • 先 queued-build ./TuistScript.sh build --scheme "MachOSwiftSection Tests" 排除编译，再 queued-build ./TuistScript.sh test --scheme "MachOSwiftSection Tests" -- -only-testing:CrossReferenceAnalysisTests。
  • 每 10 秒读一次 ps -o %cpu=,time= -p <xctest pid>，取峰值与最后的累计 CPU 时间；墙钟时间取 .xcresult。成败只认原始退出码。

调研

采样数据与代码位置
  • 2026-11-21，Ultra（28 核）：xctest 持续 2369% CPU，跑了 8 分多钟仍未结束；28 个工作线程全在 ObjectiveCClassReferenceTests.imagesReferencing → CrossReferenceAnalyzer.references(to:inImageAt:) → ReferenceScanner.scanFunction(at:)。
  • 工作线程约 11 600 个样本：栈顶是元组元数据缓存 LockingConcurrentMap<TupleCacheEntry>::getOrInsert 的 4762 个（约 41%）；经过 swift_getTupleTypeMetadata2 的约 46%，泛型元数据实例化约 13%。
  • 热点循环：RegisterFile.swift:148（for register in 0 ... 18）、RegisterFile.swift:48、ReferenceScanner.swift:150 与 :292（逐条指令的循环），都在 MachOKitExtensions 的 MachOCodeReferences。
  • 栈顶前 30 名里的自家函数只来自 MachOCodeReferences 与 ARM64InstructionDecoding；两者都没有 assert，-O 不丢检查。
  • Release 下整份 cache 两三秒扫完（AGENTS.md）；Debug 要几分钟（ObjectiveCClassReferenceTests 注释）。
  • 先例：ConcurrentDefinitionPrintingTests.taskGroupWidth = max(2, activeProcessorCount / 2)；测试 target 部署到 macOS 14，用 NSLock 而不是 Mutex。
  • Tuist 生成的工程在每个 target 的每个配置里写 SWIFT_OPTIMIZATION_LEVEL；base 能否覆盖未验证。

替代方案

7 条，均已否决
  • 改 MachOKitExtensions 的热点循环：swift test 也受益，但收益只有元数据那块、要发新版、写法变别扭；留作以后的选项。
  • 整个 Debug 工作区开 -O / 用 Release 跑测试：失去所有模块的调试能力，Release 还要另开 testability，范围远超问题。
  • CrossReferenceAnalysis、ObjCCodeReferences 也开 -O：采样里不是瓶颈；前者是本包最常调试的代码，还有一处 assert。
  • 每次调用各自限宽：并行的套件加起来又是满核。
  • 四个套件串行化：.serialized 只管套件内部，跨套件要重组结构。
  • 降低 QoS：CPU 照样占满；.background 会压到能效核，慢很多。
  • 用 concurrentMap(maximumConcurrency:)：async、跑在 cooperative pool 上，且上限按调用各算各的。

影响

  • 源码兼容性：纯新增，库的公开 API 不变。
  • ABI：不适用 —— 本库以 SPM 源码分发。
  • 下游：无；Tuist/Package.swift 只用于本仓库的开发工作区。
  • 并行的功能分支：feature/shared-macho-testing-support 也改了 FunctionStartOutsideTextTests.swift，合并时可能有小冲突。
  • API 演进：不适用，不需要版本号跃迁。
