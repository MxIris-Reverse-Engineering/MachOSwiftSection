摘要

在原生的 MachOSwiftSection.xcworkspace 之外，加一条只供日常开发用的 Tuist 路：./TuistScript.sh 生成 MachOSwiftSection-Tuist.xcworkspace。本库照常从源码编，可以跳转、可以编辑；27 个真正的第三方依赖（swift-dependencies 一族、swift-collections、Capstone、swift-crypto、Yams……）预编进本机的 Tuist 二进制缓存，只编一次。原生 workspace 里放的五个上游库——MachOKit、MachOKitExtensions、MachOObjCSection、swift-demangling、swift-semantic-string——默认按锁文件版本从源码编；加上 --local-dependencies 就改用检出旁边（worktree 里就是 .worktrees/ 下那组链接）的本地检出，没提交的改动也算，--remote-dependencies 切回，选过的模式会记住。

Tuist workspace 能跑测试：本库 21 个测试 target 由 Tuist 从 Package.swift 转换过来，依赖可执行 target 的 SwiftSectionCommandTests 在一个小的 Tuist 工程里手写；本地模式下五个上游库的测试也一起进来。做到这一点要在本库和三个上游库的 Package.swift 末尾加同一段适配，它只在 Tuist 解析时设下的环境变量下生效，平时的 SwiftPM、Xcode 与 CI 一律不受影响。RuntimeViewer 的本地依赖模式也会往这几个检出里写同名工程，两边的脚本改成共用一份占用记录，一边占着时另一边直接报错。发版、CI、swift build / swift test 和原生 workspace 都不变。

要你定

已定：本地模式下的测试

  1. 给 MachOKitExtensions、MachOObjCSection、swift-demangling 三个上游库的 Package.swift 末尾加同一段适配（默认不生效），换来本地模式下六个包的测试都能在 Tuist workspace 里跑；还是不改上游库，本地模式下不映射任何测试（RuntimeViewer 的做法，连本库自己的测试也没有）？用户选了前者：加适配块，本地模式带测试。

动机

  • 第三方依赖在每个干净的 DerivedData 里都要重编一遍。本库的依赖闭包里有 27 个与本仓库开发无关的包。原生 workspace 走 Xcode 自带的 SwiftPM 集成，每换一个 DerivedData（新 worktree、清缓存、换 Xcode）就全部从源码编一次。Tuist 的二进制缓存按内容寻址，同一台机器、同一个 Xcode 下只编一次。RuntimeViewer 用同样的做法量过：完整 App 从空 DerivedData 构建，不用缓存 504 秒，走缓存 155 秒。本库的数字还没量，第 4 步量。
  • 原生 workspace 切换本地上游库的方式太粗。今天的切换靠 USING_LOCAL_DEPENDENCIES=1 加兄弟目录是否存在（Package.swift:42 起的 package(local:remote:)）：这个变量要进到 Xcode 的启动环境里才生效；对所有声明了本地路径的依赖一刀切，连 workspace 里没有列出的 swift-capstone（Package.swift:275）也会被换成本地；切换后要等 Xcode 重新解析。Tuist 这边由 Tuist/Package.swift 按路径逐个声明要本地化的库，名单就是 workspace 的成员，切换只发生在命令行上。
  • RuntimeViewer 的本地依赖模式已经在往本仓库的检出里写工程，而没有任何东西拦着另一方。它在每个按路径声明的包目录里生成 <包名>.xcodeproj 与 Derived/。2026-11-20 实测：RuntimeViewer 的集成 worktree 正占着本库的集成 worktree，本 worktree 根目录那份被忽略的 MachOSwiftSection.xcodeproj 就是它生成的。本库自己的 Tuist 也会在同一位置生成同名工程，两边的 PackageSettings 不同，谁后生成谁就让另一边的 workspace 坏掉。

提议方案

  1. 新增 Tuist 描述，全部是开发用的：mise.toml 钉 Tuist 4.210.0（与 RuntimeViewer 相同）；Tuist/Package.swift 按路径声明本库、预编译 swift-syntax、只被测试用到的 swift-snapshot-testing，本地模式下再按路径声明五个上游库，PackageSettings 恢复警告、补 Capstone 的 trait 宏、按需调测试设置；Tuist/CommandLine/Project.swift 放 swift-section CLI、给测试用的 swift_section 模块与 SwiftSectionCommandTests；Workspace.swift 命名 MachOSwiftSection-Tuist，每个映射了测试的包一个测试 scheme（不含 IntegrationTests）；Tuist.swift 只缓存外部依赖，本库与五个上游库的全部 target 留作源码，名单由脚本经环境变量传入。
  2. Package.swift 末尾加一段适配，只在 TUIST_MAPS_LOCAL_PACKAGE_TESTS=1 时生效：摘掉依赖本包可执行 target 的测试，给测试依赖却不属于任何 product 的普通 target 补 library product。同一段代码原样加进 MachOKitExtensions、MachOObjCSection、swift-demangling。
  3. TuistScript.sh：install、generate、warm、build、test、release 六个命令，--local-dependencies / --remote-dependencies 切换并记住模式，--configuration Debug|Release，--dry-run。依赖 checkout、缓存与产物放 /Volumes/DerivedData/MachOSwiftSection/Tuist/。本地模式开始前先读各上游库的清单，有包会被 Tuist 拒掉测试时整体关掉测试映射并点名，而不是让生成失败。
  4. 占用记录两边共用：被占检出的 git 目录里写 tuist-generated-project-owner（占用者路径、释放它的命令），占用者在自己的 Tuist/.claimed-checkouts 列出手里的检出，列着才算有效。本库的脚本在任何模式下都占着自己的检出，本地模式下再占五个上游库；RuntimeViewer 的脚本改用同一份记录，旧记录仍然认。
  5. 文档：使用指南 Documentations/Internal/TuistDevelopment.md，AGENTS.md 构建一节加一条，Documentations/README.md 登记。

非目标

  • 不替代原生 workspace、swift build / swift test 与 CI；Package.swift 仍是 target 与依赖的唯一定义。
  • 不做「与原生工程对照」的 check，不重排导航栏：本库没有原生 App 工程可对照，唯一手抄的是 CLI 的依赖清单。
  • 只做 macOS，只有 Debug 与 Release 两套配置。
  • 不映射 reader-benchmark、baseline-generator，没有 regen-baselines 插件，照旧 swift run / swift package。
  • 不跑 IntegrationTests：target 会被转换进来，但不进任何 scheme。
  • 不上传缓存：不设 fullHandle。
  • MachOKit 与 swift-semantic-string 不改：实测它们现在不需要适配。
  • 不改 USING_LOCAL_DEPENDENCIES 机制：脚本运行时忽略这个变量并提示。

详细设计

Package.swift 的适配块（本库与三个上游库原样共用）

读的是 Context.environment，平时这个变量不存在，块里什么都不做；作为别人的远程依赖时也一样。探针里五个上游库副本都用它通过了 swift package dump-package 与 tuist generate。

// The Tuist development workspace (MachOSwiftSection's Documentations/Internal/TuistDevelopment.md)
// maps this package's tests with Tuist, which rejects two shapes SwiftPM accepts: a test that depends
// on an executable target, and a test that depends on a target no product contains. Only while Tuist
// resolves the packages, with TUIST_MAPS_LOCAL_PACKAGE_TESTS=1, the first kind is left out and the
// second kind gets a library product of its own. Nothing changes without the variable.
if Context.environment["TUIST_MAPS_LOCAL_PACKAGE_TESTS"] == "1" {
    let executableTargetNames = Set(package.targets.filter { $0.type == .executable }.map(\.name))
    func dependencyName(_ dependency: Target.Dependency) -> String? {
        switch dependency {
        case .targetItem(let name, _), .byNameItem(let name, _):
            return name
        default:
            return nil
        }
    }
    package.targets.removeAll { target in
        target.type == .test && target.dependencies.contains { dependency in
            dependencyName(dependency).map(executableTargetNames.contains) ?? false
        }
    }
    let productTargetNames = Set(package.products.flatMap { product in (product as? Product.Library)?.targets ?? [] })
    let testDependencyNames = Set(package.targets.filter { $0.type == .test }.flatMap { $0.dependencies.compactMap(dependencyName) })
    package.products += package.targets
        .filter { target in target.type == .regular && testDependencyNames.contains(target.name) && !productTargetNames.contains(target.name) }
        .map { target in Product.library(name: target.name, targets: [target.name]) }
}
  • 本库：摘掉 SwiftSectionCommandTests，给 SwiftSectionFixtureSupport、SwiftSectionTestingSupport（以及测试直接依赖的其余普通 target）补 product。MachOObjCSection：摘掉 ObjCSectionCommandTests。MachOKitExtensions 与 swift-demangling：补 CPlusPlusSymbolsFixture、DemanglingTestingSupport 的 product。
  • 被摘掉的测试照旧用 swift test --filter 跑；本库的 SwiftSectionCommandTests 例外，它在 Tuist/CommandLine/Project.swift 里手写。ObjCSectionCommandTests 不手写：那要在本库描述另一个仓库的 target。
  • 只看 target 依赖（targetItem / byNameItem），不看 productItem：依赖别的包的可执行 product 的测试，Tuist 怎么处理没有实测，四个包里也没有。
Tuist/Package.swift 
// swift-tools-version: 6.2
import Foundation
import PackageDescription

// The dependencies of MachOSwiftSection-Tuist.xcworkspace (Documentations/Internal/TuistDevelopment.md).
// This package is declared by path, so its Package.swift stays the only definition of its targets.
// In the local dependency mode TuistScript.sh names the upstream packages in TUIST_LOCAL_PACKAGE_NAMES
// and their directory in TUIST_LOCAL_PACKAGE_CHECKOUTS; a root's path dependency stands in for every
// declaration of the same package in the graph.
let processEnvironment = ProcessInfo.processInfo.environment
let localPackageCheckoutsDirectory = processEnvironment["TUIST_LOCAL_PACKAGE_CHECKOUTS"] ?? ""
let localPackageNames = (processEnvironment["TUIST_LOCAL_PACKAGE_NAMES"] ?? "").split(separator: ",").map(String.init)
let localPackageDependencies: [PackageDescription.Package.Dependency] = localPackageCheckoutsDirectory.isEmpty
    ? []
    : localPackageNames.map { packageName in .package(path: "\(localPackageCheckoutsDirectory)/\(packageName)") }

#if TUIST
    import ProjectDescription

    func names(_ variable: String) -> [String] {
        (processEnvironment[variable] ?? "").split(separator: ",").map(String.init)
    }

    // Tuist suppresses warnings in every package; Xcode does so for remote packages only.
    let warningSettings: [String: Settings] = Dictionary(
        names("TUIST_WARNING_TARGET_NAMES").map { targetName in
            (targetName, Settings.settings(base: ["SWIFT_SUPPRESS_WARNINGS": "NO", "GCC_WARN_INHIBIT_ALL_WARNINGS": "NO"]))
        },
        uniquingKeysWith: { first, _ in first }
    )

    // Tuist drops a setting whose only condition is a trait; this package enables swift-capstone's
    // AARCH64 trait, which defines CAPSTONE_HAS_AARCH64 that way.
    let restatedTraitDefinitions: [String: Settings] = [
        "Capstone": .settings(base: [
            "SWIFT_ACTIVE_COMPILATION_CONDITIONS": ["$(inherited)", "CAPSTONE_HAS_AARCH64"],
            "GCC_PREPROCESSOR_DEFINITIONS": ["$(inherited)", "CAPSTONE_HAS_AARCH64=1"],
        ]),
        "Ccapstone": .settings(base: [
            "GCC_PREPROCESSOR_DEFINITIONS": ["$(inherited)", "CAPSTONE_HAS_AARCH64=1"],
        ]),
    ]

    // Filled in by step 2 once the tests have been built: the deployment target SwiftPM gives a test
    // target (macOS 14.0) and -ObjC, each only if the build shows it is needed.
    let testTargetSettings: [String: Settings] = [:]

    let packageSettings = PackageSettings(
        targetSettings: warningSettings
            .merging(restatedTraitDefinitions) { $1 }
            .merging(testTargetSettings) { $1 },
        includeLocalPackageTestTargets: processEnvironment["TUIST_MAPS_LOCAL_PACKAGE_TESTS"] == "1"
    )
#endif

let package = Package(
    name: "MachOSwiftSectionTuistDependencies",
    dependencies: [
        .package(path: ".."),
        // Stands in for swift-syntax everywhere, as it does as a member of the native workspace.
        .package(path: "../PrecompiledLibraries/swift-syntax"),
        // Used only by tests, which Tuist needs declared here (MachOSwiftSection's requirement).
        .package(url: "https://github.com/pointfreeco/swift-snapshot-testing", from: "1.18.9"),
    ] + localPackageDependencies
)
  • 根包的路径依赖 .. 的身份是目录名：worktree 叫 MachOSwiftSection-<用途> 时身份就变了，而上游库的清单不按 URL 引用本库，所以不受影响；生成的工程名取自 Package(name:)，仍是 MachOSwiftSection.xcodeproj。
  • TUIST_WARNING_TARGET_NAMES 是本库全部 target，本地模式下再加五个上游库的全部 target（与原生 workspace 一致：Xcode 只给远程包关警告）。

// SwiftSectionCommandTests, which imports the executable's module. swift_section compiles the same
// sources as a static framework for that test; the tool compiles them again, so its link needs no
// trick around the @main entry point. The dependency list mirrors Package.swift's swift-section
// target and is the one hand-written copy in the Tuist description.

    .external(name: "SwiftSectionKit"),
    .external(name: "MachOFoundation"),
    .external(name: "SwiftSymbols"),
    .external(name: "SwiftDump"),
    .external(name: "SwiftOutputTransformer"),
    .external(name: "SwiftDeclaration"),
    .external(name: "SwiftIndexing"),

Workspace.swift 
import ProjectDescription

// "<package directory>=<test target>,<test target>;…" from TuistScript.sh, one entry per package whose
// tests are mapped: this package always (directory "."), the upstream packages in the local mode.
// IntegrationTests is never listed.
let packageTestTargets: [(directory: String, targets: [String])] = Environment.packageTestTargets
    .getString(default: "")
    .split(separator: ";")
    .compactMap { entry in
        let parts = entry.split(separator: "=", maxSplits: 1).map(String.init)
        guard parts.count == 2 else { return nil }
        return (parts[0], parts[1].split(separator: ",").map(String.init))
    }

let workspace = Workspace(
    name: "MachOSwiftSection-Tuist",
    projects: ["Tuist/CommandLine"],
    schemes: packageTestTargets.map { entry in
        let packageName = entry.directory == "." ? "MachOSwiftSection" : (entry.directory as NSString).lastPathComponent
        var testableTargets = entry.targets.map { targetName in
            TestableTarget.testableTarget(target: .project(path: Path(entry.directory), target: targetName))
        }
        if entry.directory == "." {
            testableTargets.append(.testableTarget(target: .project(path: "Tuist/CommandLine", target: "SwiftSectionCommandTests")))
        }
        return .scheme(name: "\(packageName) Tests", testAction: .targets(testableTargets))
    }
)
  • 上游库的目录是绝对路径；Path 接受绝对路径字符串，第 3 步验证。Workspace.swift 能否 import Foundation 用 NSString 没验证，不行就自己切最后一段。
  • 测试映射被预检关掉时 TUIST_PACKAGE_TEST_TARGETS 为空，只剩各 target 自己的 scheme；SwiftSectionCommandTests 仍在 MachOSwiftSectionCommandLine 工程里，Tuist 自动生成的 scheme 能跑它。

命令

命令做什么
install从种子锁文件开始解析当前模式的依赖（tuist install），结束时与种子比对 pin
generate [--configuration <c>]需要时先 install，占用检出，生成 workspace（默认 Debug）
warm [--configuration <c>]带 --cache-profile development 把第三方依赖编进缓存，再生成
build [--configuration <c>]生成后用 xcodebuild 编 swift-section scheme
test [-- <xcodebuild 参数>]生成后用 xcodebuild test 跑 MachOSwiftSection Tests scheme，退出码就是 xcodebuild 的
release放弃所有占用：删掉生成进各检出的工程（git 跟踪的不删）、占用记录与 MachOSwiftSection-Tuist.xcworkspace；Derived/ 留着

--local-dependencies / --remote-dependencies 可以跟在任何命令后面，从这条命令起切换模式；--dry-run 打印要做的事；--help 打印脚本头部的说明。

名单从哪来

本地依赖的名字读 MachOSwiftSection.xcworkspace/contents.xcworkspacedata 里的 container:../<名字>（不含 / 的那些），workspace 加了库这里自动跟上。target 名单用 swift package dump-package（带 TUIST_MAPS_LOCAL_PACKAGE_TESTS=1，--scratch-path 放在 Work/<checkout>/Manifests/）读六个包的清单：本库与本地模式下的上游库读检出里的，远程模式下的上游库读 install 之后 SWIFTPM_BUILD_DIR/checkouts/<名字> 里的。远程模式下第一次 install 之前还没有 checkout，先用空名单装一次再算。

测试映射的预检

对每个按路径声明的包，在它的清单 JSON 里找 Tuist 会拒绝的两种形态——测试依赖本包的可执行 target、测试依赖不属于任何 product 的普通 target。适配块生效时这两种都不该剩下；还剩，说明那个包没有适配块（比如本地检出停在加块之前的提交），这次就整体设 TUIST_MAPS_LOCAL_PACKAGE_TESTS=0，警告点名那个包，生成照常进行。只被测试用到的外部依赖预检查不出来，生成时 Tuist 自己会报，指南里写怎么补。

锁文件

Tuist/Package.resolved 不提交（*.resolved 已忽略）。每次 install 前用本检出根目录的 Package.resolved 当种子（没有就不种），结束时逐条比对，不同就警告；swift-syntax（这边是预编译包，没有 pin）与本地模式下的五个库不参与比对。

依赖模式

模式记在 Tuist/.local-dependencies（内容是上游库所在目录；远程模式下这个文件不存在）。默认目录是检出的上一级，worktree 里就是 .worktrees/；打开本地模式时设了 TUIST_LOCAL_PACKAGE_CHECKOUTS 就用它。两种模式各用一份依赖 checkout，共用 Tuist/Package.resolved，所以切换后、或上次解析用的是另一种模式时先重新 install。切到远程时释放五个上游库的占用。

存放位置

/Volumes/DerivedData 挂着时全放在 /Volumes/DerivedData/MachOSwiftSection/Tuist/ 下（Cache/、Dependencies/<checkout>[-LocalDependencies]/、WarmScratch/<checkout>/、Work/<checkout>/），<checkout> 是目录名加路径的短 hash；没挂载时放在仓库里的 Tuist/.build/、Tuist/.build-LocalDependencies/ 与 DerivedData/Tuist/。TUIST_SCRIPT_ROOT 指定别处。build / test 的 DerivedData 在 Work/<checkout>/DerivedData。日志在 Products/Logs/Tuist/；Tuist 的输出原样显示并记进日志，xcodebuild 的输出只进日志，失败时显示错误摘要。

占用记录（与 RuntimeViewer 共用）

  • 被占的检出：它的 git 目录（git rev-parse --absolute-git-dir，worktree 各有一份）里的 tuist-generated-project-owner，第一行是占用者检出的路径，第二行是在占用者检出里释放它的命令。
  • 占用者：自己的 Tuist/.claimed-checkouts，每行一个被占检出的真实路径（pwd -P）。
  • 有效：占用者的 .claimed-checkouts 列着这个路径。占用者不在了、或已经不列了，记录就是陈旧的，可以直接覆盖。
  • 旧记录 runtimeviewer-tuist-local-dependencies：占用者的 Tuist/.local-dependencies 加上包名指向这个检出时算有效（RuntimeViewer 今天的规则）。
  • 本库的脚本在 generate 前占用自己的检出与（本地模式下）五个上游库；遇到别人的有效占用就失败，报出占用者路径与它的释放命令。检出里 git 跟踪着 <包名>.xcodeproj 时也失败。上游库的生成物写进那个仓库的 info/exclude，本库自己的走 .gitignore。
  • 释放：删掉生成进那个检出的工程、占用记录，并从 .claimed-checkouts 里去掉。

Tuist 版本与 agent 运行

读 mise.toml 的版本；有 mise 就 mise exec -- tuist，否则用 PATH 里的 tuist；版本不对就失败并提示 mise install。agent 运行时设 TUIST_SCRIPT_ROOT=/Volumes/DerivedData/Agents.noindex/<agent>/Tuist-MachOSwiftSection，并写成 queued-build ./TuistScript.sh <命令>。

RuntimeViewer 那一侧
  • claim_local_checkouts：先读共用记录与旧记录，任何一个有效且占用者不是自己就失败，报出占用者与释放命令；然后写共用记录（第二行是 ./TuistScript.sh generate --remote-dependencies），把路径写进自己的 Tuist/.claimed-checkouts，自己的旧记录删掉。
  • release_local_checkouts：删掉自己的共用记录（以及残留的旧记录），从 .claimed-checkouts 里去掉。
  • 今天它占着本库的集成 worktree 与五个上游检出（旧记录）。改完后它下一次 generate 就把记录换成新的；在那之前，本库的脚本按旧规则认出它的占用。

调研

现状
  • 原生 workspace 的成员：container:../MachOKit、container:../MachOObjCSection、group:（本库）、group:PrecompiledLibraries/swift-syntax。集成 worktree 里还有一处没提交的改动，又加了 container:../MachOKitExtensions、container:../swift-demangling、container:../swift-semantic-string。「本地依赖」指的就是这五个成员。
  • PrecompiledLibraries/swift-syntax 是一个按包身份顶替 swift-syntax 的包，每个 product 是一个 binaryTarget（PrecompiledLibraries/swift-syntax/Package.swift:46 起）。Tuist 这边要在 Tuist/Package.swift 里按路径声明它，两种模式都声明。
  • 本库 Package.swift 的本地依赖开关：usingLocalDependencies = envEnable("USING_LOCAL_DEPENDENCIES")（Package.swift:42）；package(local:remote:) 在 #filePath 含 /checkouts/、/SourcePackages/ 或 /.build/ 时一律走远程（Package.swift:49-74）。

  • 没有提交的锁文件：.gitignore 有 *.resolved。
  • RuntimeViewer 的做法：Tuist/Package.swift 按路径声明四个本地包；缓存 profile 按名字把本地包与 MachO 那几个库的 target 留作源码；本地依赖模式记在 Tuist/.local-dependencies，两种模式各用一份 SWIFTPM_BUILD_DIR；占用记录写在被占检出的 git 目录里，有效与否看占用者的 Tuist/.local-dependencies；切回远程时删掉生成进库目录的工程；Tuist 生成的文件经 info/exclude 忽略。它的本地模式不映射测试，原因正是实测第 1 条与第 6 条。它钉的 Tuist 是 4.210.0。

替代方案

九条，都否了（或暂否）
  • Tuist 的「把 Package.swift 当工程」（beta）：切换仍要一个根清单按路径声明上游库；不打算支持 SwiftPM 全部特性；很可能按包名生成与原生同名的 workspace（推测）。否。
  • 在 Project.swift 里手写全部 target：冲突自然消失，但五十来个 target 的依赖要再抄一份，必然漂移。否。
  • Tuist 的 Xcode 原生包集成：不往包目录写工程，但没有二进制缓存，与原生 workspace 相比什么也没得到。否。
  • 本地模式不映射测试（RuntimeViewer 的做法）：不用改上游库；但跨仓库改动时用的正是本地模式，那时连本库自己的测试也跑不了。用户选了加适配块。
  • 只针对点名的 target 打补丁：三个上游库各写一份不同的补丁，以后每加一个这种形态的测试都要回来改。否。
  • CLI 只链 framework、不带源码：省一遍编译，但能否链接成功没实测。否，第 2 步可以顺手试。
  • 远程模式下把五个上游库也放进缓存：更快，但 pin 动得勤、要反复预热，也跳不进源码。暂否，第 4 步量出差距后可重议。
  • 只在本库这边检查 RuntimeViewer 的占用：RuntimeViewer 照样会盖掉本库生成的工程。用户选了双向互斥。
  • 用 USING_LOCAL_DEPENDENCIES=1 实现本地模式：对所有带本地路径的依赖一刀切（含 swift-capstone），三个上游库的清单也各有自己的开关。否。

影响

  • 源码兼容性：纯新增，没有任何公开 API 变化。适配块只在 TUIST_MAPS_LOCAL_PACKAGE_TESTS=1 时生效，swift build、swift test、原生 workspace、CI 与下游的 SwiftPM 解析都不会设这个变量。
  • ABI 兼容性：不适用——本库以 SPM 源码分发，使用方每次重新编译。
  • 本仓库内：没有 target 受影响；.gitignore 多几项，workspace 多三个成员。
  • RuntimeViewer：脚本换用共用的占用记录。它的 Tuist 不设那个变量，适配块不生效，它生成的工程不变。
  • 三个上游库：清单末尾多一段默认不生效的代码，不需要发版。其他下游（MachOKitUI、SymbolViewer……）不受影响。
  • 文档：新增使用指南并登记；AGENTS.md 加一条；README.md 不改；RuntimeViewer 的指南改两段。
  • API 演进与废弃：无。
