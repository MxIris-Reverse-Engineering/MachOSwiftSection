摘要

六个 MachO 系列包里有五个已经在 Swift 6 语言模式下编译，complete strict concurrency checking 早已按错误执行；唯一的例外是 MachOKit（fork），它的清单还是 swift-tools-version: 5.10。本提案做两件事：把 MachOKit 升到 tools 6.0，让它也进入 Swift 6 语言模式（实测零错误，Sources 里零并发诊断；停在 6.0 而不是 6.2，是为了 fork 的 CI 所用的 Swift 6.0 工具链还读得了清单）；然后在六个包的每个 Swift target 上开启 ExistentialAny、MemberImportVisibility、InferIsolatedConformances 三项 upcoming feature（编译器把它们标为 Swift 7 默认开启），开关在每份清单末尾用一个循环统一加，不逐个 target 写。

源码改动 723 处（717 个 fix-it 加 6 处预修），绝大部分是补 import 与补 any，源码与测试都由 swift package --build-system native migrate 自动改出；另有 6 处工具处理不了、要先手工改好，它写成 internal import 的补丁按各仓库的惯例改回普通 import。同为 Swift 7 默认的 NonisolatedNonsendingByDefault、InternalImportsByDefault、ImmutableWeakCaptures，以及独立的 StrictMemorySafety，量过之后明确不做。

提议方案与非目标

  1. MachOKit 进 Swift 6 语言模式。第 1 行改成 // swift-tools-version: 6.0，tools 6.x 不声明 swiftLanguageModes 时默认 Swift 6。不用 6.2：fork 的 CI 在 Xcode 16.2 与 Linux Swift 6.0.3 上编，6.2 的清单它们读不了；编译器不认识的特性名会被忽略，6.0 照样能编。删掉九项 Swift 6 已默认开启的 upcoming setting 与 CaseIterable 扩展；AccessLevelOnImport 保留。
  2. 六个包的每个 Swift target 统一开启三项特性。每份清单在 let package = Package(...) 之后加一个循环，给除 system、binary、plugin 以外的所有 target 追加同一组设置；本库沿用 Package.swift:1541 已有的常量。
  3. 源码由 migrate 改，前后各补一手。先改好 6 处预修；在清单还没开特性时跑 swift package --build-system native migrate，源码与测试一起改；丢弃它对清单的改动；把 internal import X 改回普通 import X，除非仓库本来就 internal import 这个模块；最后加开关，正式开启后编一遍确认零错误。
  4. 每加一条 import Semantic，就检查裸写的 Error、Numeric、Argument。类型位置写 Swift.Error；转型与 catch 模式逐个看；「cast always fails」警告按错误对待。
  5. 从下往上落地，不为此单独发版。设置只影响包自身的编译，不改公开 API。

非目标

  • 不开 NonisolatedNonsendingByDefault、InternalImportsByDefault、ImmutableWeakCaptures、StrictMemorySafety。
  • 不动 FrameworkToolbox（不属于 MachO 系列）。
  • 不给 swift-semantic-string 的 Error、Numeric、Argument 改名（公开 API 破坏）。
  • 不清理现有的 @unchecked Sendable（本库 84 处）与 nonisolated(unsafe)（37 处）。
  • 不采用 typed throws、~Copyable、Span 等新语言特性。
  • 不把这些改动提给上游 p-x9/MachOKit。

详细设计

统一开关 
let upcomingFeatureSettings: [SwiftSetting] = [
    .enableUpcomingFeature("ExistentialAny"),
    .enableUpcomingFeature("MemberImportVisibility"),
    .enableUpcomingFeature("InferIsolatedConformances"),
]

for target in package.targets where target.type != .system && target.type != .binary && target.type != .plugin {
    target.swiftSettings = (target.swiftSettings ?? []) + upcomingFeatureSettings
}

swift-semantic-string 与 MachOKit 写在清单末尾；swift-demangling、MachOKitExtensions、MachOObjCSection 写在末尾的 Tuist 块之前；本库写在 extension SwiftSetting 之后、Tuist 块之前，数组里用已有的 .existentialAny、.memberImportVisibility、.inferIsolatedConformances。

迁移命令与 internal import 的处理 
queued-build swift package --build-system native \
    --scratch-path /Volumes/DerivedData/Agents.noindex/claude/SwiftPM/MachOSwiftSection-Swift6UpcomingFeatures-Migrate \
    migrate --to-feature ExistentialAny,MemberImportVisibility,InferIsolatedConformances
git checkout -- Package.swift

不带 --target 就连测试一起改；--build-system native 不能省。本库退出码是 1 属正常（改清单失败），以 Applied N fix-its 为准。对每一行新加的 internal import X：仓库原来有 internal import X 的保留，没有的改成普通 import X。

swift package migrate 的实际表现与迁移的坑
  • 本库清单写成 extension Target 上的静态常量，migrate 改清单那一步失败，源码照样改好；清单一律手改。
  • 默认构建系统下 migrate 不改测试（450 条测试警告、0 个 fix-it）；--build-system native 下一遍改完源码与测试。
  • native 构建系统下它常写 internal import X，与别的文件的普通 import X 冲突（本库 17 个文件报访问级别有歧义）。
  • 迁移模式本身有 4 处硬错误（switch 不完备、.enum 解析成实例成员、两处 .values 落到 dynamic member lookup），构建一失败 migrate 就一处都不改，所以要预修。
  • swift-semantic-string 公开声明了 Error、Numeric、Argument；文件直接 import Semantic 后裸 Error 就是 Semantic.Error：源码 2 处、测试 14 个文件编不过，改成 Swift.Error。
  • Swift 6.4 的 fix-it 写出 any P?，Swift 6.3 要求 (any P)?：三处。
  • MachOKit 进 Swift 6 模式后，测试二进制里一个 curry thunk 的 mangling 多了 Yb（SE-0418），按名字找它的测试要跟着改。

替代方案

八条，都否了或改了形状
  • MachOKit 只加 StrictConcurrency：Swift 5 模式下只是警告，约束力不够。
  • MachOKit 用 swiftLanguageVersions: [.version("6")]：写法与兄弟包不一致，上游冲突也省不掉。
  • MachOKit 用 tools 6.2：草案原定；fork 的 CI 用 Swift 6.0，读不了。改为 6.0。
  • 测试照警告手改或写批量脚本：草案原定；--build-system native 的 migrate 就能改测试。
  • 逐个 target 写或让 migrate 改清单：容易漏；migrate 在本库清单上直接失败。选统一循环。
  • 四项全开：用户选了只开三项低风险的。
  • 不开 MemberImportVisibility：它是「依赖写在自己的 import 里」的来源，坑都已找全。保留。
  • 给 Semantic.Error 改名：公开 API 破坏，不在本次范围。

影响

  • 源码兼容性：纯新增。六个包都不改任何公开声明的签名；upcoming feature 只作用于开启它的 target 本身，不传给下游。
  • ABI：不适用，SPM 源码分发。
  • 下游：RuntimeViewer、MachOKitUI、SymbolViewer 不用改代码。上游 p-x9/MachOKit 不提交，合上游 tag 时清单两处会冲突，按 fork 写法解决。
  • 文档：账本加一节、索引登记；CLAUDE.md 预计不加条目，落地时再判断。
  • API 演进：没有废弃的 API，不需要 major 跃迁，不单独发版。
